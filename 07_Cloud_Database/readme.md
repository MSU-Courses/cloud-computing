## Хранилище и база данных

В шестой главе мы научились хранить файлы в _Amazon S3_. Хранить там же заказы интернет-магазина, например по одному JSON-объекту на заказ, неудобно по двум причинам:

- _Поиск по содержимому_. S3 выдаёт объект по ключу, но не заглядывает внутрь объектов. Чтобы найти заказы клиента 42 за октябрь, приложению придётся скачать и разобрать все заказы магазина.
- _Одновременные изменения_. По умолчанию объект перезаписывается целиком, и побеждает последняя запись. Если два покупателя одновременно купят последний товар, оба запроса прочитают остаток "1", оба запишут "0", и товар будет продан дважды.

Эти задачи решает база данных.

**База данных (database)** - организованный набор данных, который хранится и обрабатывается системой управления, умеющей искать данные по их содержимому, изменять отдельные значения и согласовывать одновременные изменения.

**СУБД (система управления базами данных, database management system, DBMS)** - программа, которая хранит базу данных и выполняет запросы к ней, например PostgreSQL или MySQL.

| Свойство                | Объектное хранилище (Amazon S3)               | База данных                                     |
| ----------------------- | --------------------------------------------- | ----------------------------------------------- |
| Как находят данные      | По имени файла или ключу объекта              | По содержимому: любому полю или их сочетанию    |
| Изменение               | Объект перезаписывается целиком               | Изменяется отдельное поле отдельной записи      |
| Одновременные изменения | По умолчанию побеждает последняя запись       | СУБД согласует их и не даёт потерять ни одно    |
| Типичные данные         | Фотографии, документы, видео, резервные копии | Пользователи, заказы, остатки на складе, сессии |

База данных не заменяет хранилище, а работает вместе с ним. Фотография товара лежит в S3, а в базе данных хранится запись о товаре с его названием, ценой и ключом этой фотографии в бакете.

## Типы баз данных

### Реляционные базы данных (RDBMS)

Базы данных бывают разных типов, и самый распространённый из них появился задолго до облаков.

**Реляционная база данных (relational database)** - база данных, в которой данные хранятся в таблицах из строк и столбцов, а связи между таблицами задаются через значения ключей[^1].

**Схема (schema)** - описание структуры базы данных: какие в ней таблицы, какие у них столбцы, какого типа данные хранятся в каждом столбце и какие действуют ограничения.

Связи между таблицами строятся на двух видах ключей:

- _Первичный ключ (primary key)_. Столбец, значение которого однозначно определяет строку таблицы, например `customer_id` в таблице клиентов.
- _Внешний ключ (foreign key)_. Столбец, который ссылается на первичный ключ другой таблицы и тем самым связывает строки двух таблиц[^1].

На рисунке 7.1 показаны три таблицы учебного интернет-магазина: клиенты, товары и заказы. В таблице `orders` столбцы `customer_id` и `product_id` являются внешними ключами: они указывают, какой клиент сделал заказ и какой товар он купил.

С реляционной базой работают на языке SQL (Structured Query Language), который вы уже встречали в курсе по базам данных.

Вторую проблему из начала главы, одновременные изменения, реляционные СУБД решают транзакциями.

**Транзакция (transaction)** - группа операций с базой данных, которую СУБД выполняет как одно целое: либо все операции применяются, либо ни одна[^2].

Оформление заказа, то есть создание заказа и уменьшение остатка на складе, выполняют _одной транзакцией_.

Если два покупателя одновременно покупают последний товар, СУБД не позволит двум транзакциям менять одну и ту же строку остатка в одно и то же время:

- вторая транзакция дождётся завершения первой и увидит остаток "0",
- поэтому вторая покупка будет отменена.

_Основные характеристики_ реляционных баз данных:

- _Таблицы и схема_. Данные хранятся в таблицах, структура которых заранее задана схемой.
- _Связи через ключи_. Таблицы связаны первичными и внешними ключами, а данные из нескольких таблиц объединяют операцией `JOIN`.
- _Язык SQL_. Запрос к данным записывают на SQL, и СУБД выполнит даже тот запрос, о котором не думали при проектировании базы.
- _Транзакции_. Несколько изменений выполняются как одно целое, а одновременные изменения одних и тех же строк СУБД согласует сама.
- _Примеры СУБД_. PostgreSQL, MySQL, MariaDB, Oracle Database, Microsoft SQL Server.

### Ограничения реляционной модели

Реляционная модель удобна, но с ростом приложения у неё проявляются два ограничения:

- _Жёсткая схема_. Схема задаётся заранее, и любое новое поле требует её изменения. Если у товаров магазина свойства сильно различаются (у ноутбука есть объём памяти, у футболки размер, у книги автор), таблица превращается либо в десятки полупустых столбцов, либо в набор дополнительных таблиц.
- _Масштабирование_. Реляционную базу обычно масштабируют, увеличивая мощность одного сервера, а распределить чтение и запись по многим серверам можно только особыми приёмами[^3]. Почему так происходит, разберём в следующем разделе ["Масштабирование баз данных"](#масштабирование-баз-данных).

Ответом на эти ограничения стали нереляционные базы данных.

### Нереляционные базы данных

**Нереляционная база данных (non-relational database, NoSQL)** - база данных, которая хранит данные не в связанных таблицах, а в модели, выбранной под конкретный вид данных и запросов[^4]:

- в парах ключ-значение,
- в документах,
- в графах,
- в других моделях.

Название NoSQL часто расшифровывают как "_not only SQL_", потому что многие такие базы поддерживают и похожие на SQL языки запросов. Основные модели данных перечислены в таблице.

| Модель                       | Как хранятся данные                                        | Пример задачи                                            |
| ---------------------------- | ---------------------------------------------------------- | -------------------------------------------------------- |
| Ключ-значение (key-value)    | Пары "ключ и значение", поиск только по ключу              | Корзина покупателя, сессия пользователя                  |
| Документная (document)       | Документы в формате, похожем на JSON, со вложенными полями | Карточки товаров с разным набором свойств                |
| Колоночная (wide-column)     | Таблицы, в которых у каждой строки свой набор столбцов     | Журналы событий огромного объёма                         |
| Графовая (graph)             | Узлы и связи между ними                                    | Рекомендации "с этим товаром покупают", социальные связи |
| В памяти (in-memory)         | Данные целиком в оперативной памяти                        | Кеш часто запрашиваемых страниц                          |
| Временные ряды (time series) | Значения, привязанные ко времени                           | Показания датчиков, метрики серверов                     |

Модели разные, но для разработчика у них есть общая особенность. Данные в нереляционной базе раскладывают так, чтобы нужный запрос выполнялся по ключу. Произвольный запрос может оказаться медленным или вовсе невозможным[^3][^4].

_Основные характеристики_ нереляционных баз данных[^3][^4]:

- _Модель под задачу_. Вместо связанных таблиц используется модель, удобная для конкретных данных: ключ-значение, документы, графы и другие.
- _Гибкая схема_. Записи одной таблицы или коллекции могут иметь разный набор полей, и новое поле не требует менять структуру базы.
- _Распределение по многим серверам_. Данные и нагрузку можно разложить по многим серверам, поэтому такие базы рассчитаны на большие объёмы и большое число запросов.
- _Запросы проектируют заранее_. Данные раскладывают так, чтобы нужный запрос выполнялся по ключу. Произвольный запрос, которого не было в проекте, может оказаться медленным или вовсе невозможным.
- _Ограниченные объединения и транзакции_. Операции `JOIN` обычно нет, а транзакции поддерживаются не везде или с ограничениями.
- _Примеры СУБД_. MongoDB, Redis, Apache Cassandra, Amazon DynamoDB.

### Как выбрать тип базы данных

Ни один тип не лучше другого во всём. Выбор зависит от того, какие данные хранит приложение и какие запросы к ним выполняет.

| Свойство         | Реляционная база                            | Нереляционная база                                  |
| ---------------- | ------------------------------------------- | --------------------------------------------------- |
| Структура данных | Таблицы с фиксированной схемой              | Модель под задачу, гибкая схема                     |
| Запросы          | Любые запросы на SQL, объединение таблиц    | В основном по ключу, запросы проектируют заранее    |
| Транзакции       | Полноценные транзакции                      | Зависит от базы, часто с ограничениями              |
| Масштабирование  | Обычно вертикальное                         | Обычно горизонтальное                               |
| Типичные данные  | Заказы, платежи, учёт, всё, где важны связи | Корзины, сессии, каталоги, события, огромные объёмы |

Часто в одном приложении используют _обе модели_. Например, в интернет-магазине:

- заказы и платежи требуют транзакций и попадают в реляционную базу,
- корзины покупателей читаются и пишутся только по идентификатору пользователя и хорошо ложатся в модель ключ-значение.

## Масштабирование баз данных

### Вертикальное и горизонтальное масштабирование

Пока магазин небольшой, одного сервера базы данных хватает. С ростом числа покупателей сервер перестаёт справляться:

- запросы выполняются медленнее,
- процессор загружен постоянно.

Увеличить производительность можно двумя способами:

**Вертикальное масштабирование (vertical scaling, scale up)** - увеличение мощности одного сервера: больше процессоров, памяти, быстрее диск.

**Горизонтальное масштабирование (horizontal scaling, scale out)** - добавление новых серверов, между которыми распределяется нагрузка.

| Признак                  | Вертикальное масштабирование                                         | Горизонтальное масштабирование                |
| ------------------------ | -------------------------------------------------------------------- | --------------------------------------------- |
| Как выполняется в облаке | Сменой типа экземпляра на более мощный                               | Добавлением экземпляров                       |
| Предел роста             | Самый крупный тип экземпляра когда-нибудь закончится                 | Жёсткого предела нет                          |
| Что замечает приложение  | Смена типа требует перезапуска экземпляра, то есть короткого простоя | Ничего, если нагрузку умеют распределять      |
| Отказоустойчивость       | Один сервер остаётся одной точкой отказа                             | Отказ одного сервера не останавливает систему |

Горизонтальное масштабирование для базы данных намного сложнее, чем для веб-серверов. Веб-сервера не хранят состояние и могут легко добавляться или удаляться. Серверы базы данных хранят состояние, и каждое изменение данных должно стать известно всем серверам, которые отдают эти данные[^5].

Для этого используют два приёма:

- копирование всех данных на несколько серверов,
- разделение данных между ними.

Разберём их по очереди.

### Репликация в базах данных

**Репликация** - это непрерывное копирование изменений из одного хранилища в другое.

Разделяют два основных понятия:

**Основной сервер (primary)** - сервер базы данных, который принимает операции записи.

**Реплика (replica)** - сервер базы данных, который получает изменения от основного сервера и хранит копию его данных[^5].

Чтобы понять, как изменения попадают на реплику, нужен ещё один механизм.

**Журнал транзакций (write-ahead log, WAL)** - файл, в который СУБД перед изменением самих данных дописывает описание каждого изменения[^6].

Журнал нужен СУБД и без репликации: если сервер внезапно выключится, при запуске СУБД восстановит по журналу изменения, которые успела подтвердить[^6].

Репликация использует тот же журнал. Основной сервер передаёт его записи репликам, а реплики применяют те же изменения в том же порядке и поэтому хранят те же данные. В PostgreSQL этот механизм называется **потоковой репликацией** (_streaming replication_)[^7].

Репликация решает две задачи:

- _Отказоустойчивость_. Если основной сервер отказал, одна из реплик может занять его место[^5].
- _Масштабирование чтения_. Реплики могут обслуживать запросы на чтение, разгружая основной сервер[^5].

**Переключение при отказе (failover)** - перевод реплики в роль основного сервера после того, как основной сервер отказал.

По тому, какие серверы принимают запись, различают две схемы репликации[^5]:

- _Один основной сервер (leader-follower)_. Запись принимает только основной сервер, а реплики получают от него изменения и могут обслуживать чтение. Эту схему называют также _primary-replica_, а в старых источниках _master-slave_. Если основной сервер отказал, одну из реплик назначают основной.
- _Несколько основных серверов (leader-leader, multi-master)_. Запись принимают сразу несколько серверов и пересылают изменения друг другу. Если одну и ту же строку одновременно изменили на двух серверах, например один администратор поменял цену товара, а другой снял его с продажи, возникает конфликт, и нужны правила, по которым решают, чьё изменение победит.

Из-за конфликтов в большинстве приложений используют первую схему. С ней мы и будем работать в AWS.

### Синхронная и асинхронная репликация

Когда основной сервер может сообщить приложению, что транзакция сохранена? Возможны два ответа.

![Синхронная и асинхронная репликация: когда приложение получает подтверждение](../_images/07/sync_async.svg)

_7.2. Синхронная и асинхронная репликация: когда приложение получает подтверждение_

**Синхронная репликация (synchronous replication)** - режим, в котором основной сервер подтверждает транзакцию приложению только после того, как реплика подтвердила получение изменений[^7].

**Асинхронная репликация (asynchronous replication)** - режим, в котором основной сервер подтверждает транзакцию сразу, а изменения передаются реплике с небольшой задержкой.

У каждого режима своя цена:

- _Синхронная репликация_ гарантирует, что при переключении на реплику ни одна подтверждённая транзакция не потеряется. Платить за это приходится скоростью: каждая запись ждёт как минимум время сетевого обмена между серверами, а при медленной сети производительность может упасть вдвое и больше[^7][^5].
- _Асинхронная репликация_ не замедляет запись, но если основной сервер откажет до того, как изменения дошли до реплики, последние транзакции будут потеряны[^5].

Этот выбор напрямую связан с _RPO_, о котором мы говорили в прошлой главе.

- Синхронная реплика даёт _RPO_, близкий к нулю.
- У асинхронной реплики _RPO_ равен её отставанию от основного сервера: обычно оно небольшое, но при перегрузке растёт. В правой части рисунка 7.2 это окно потери данных показано между подтверждением транзакции и её доставкой на реплику.

### Реплики для чтения

Посмотрим на нагрузку интернет-магазина. Покупатели в основном читают:

- открывают каталог,
- ищут товары,
- смотрят свои заказы.

Запись происходит реже:

- оформление заказа,
- отзыв о товаре,
- изменение профиля.

Если чтение в десятки раз чаще записи, основной сервер тратит большую часть времени на чтение.

**Реплика для чтения (read replica)** - реплика, которая принимает только запросы на чтение и служит для разгрузки основного сервера.

Приложение отправляет все операции записи на основной сервер, а запросы на чтение распределяет между репликами, как показано на рисунке 7.3. Чтобы увеличить мощность чтения, достаточно добавить ещё одну реплику.

![Запись идёт на основной сервер, чтение распределяется между репликами](../_images/07/read_replicas.svg)

_7.3. Запись идёт на основной сервер, чтение распределяется между репликами_

Реплики для чтения почти всегда _асинхронные_. Поэтому между записью на основном сервере и её появлением на реплике проходит время.

**Задержка репликации (replication lag)** - время, на которое данные реплики отстают от данных основного сервера.

Из-за задержки возникает неприятный эффект:

1. Пользователь меняет адрес доставки.
2. Запрос на запись уходит на основной сервер, и приложение сразу перезагружает страницу профиля.
3. Запрос на чтение попадает на реплику, до которой изменение ещё не дошло.
4. Пользователь видит старый адрес.

Ему кажется, что сохранение не сработало.

Обычно эту проблему решают так: запросы, которым нужны только что записанные данные, отправляют на основной сервер. _Например_, страницу профиля сразу после сохранения читают с основного сервера, а каталог товаров, где отставание на секунду никому не мешает, с реплик.

> [!IMPORTANT]
> Реплика для чтения не ускоряет запись: все изменения по-прежнему проходят через один основной сервер, а потом ещё и копируются на каждую реплику. Реплики помогают, когда узкое место в чтении.

### Шардирование

Реплики помогают с чтением, но не с записью и не с объёмом данных: _каждая реплика хранит полную копию базы_. Представим, что магазин вырос до миллионов заказов в день. Один основной сервер не успевает записывать заказы, а таблица заказов не помещается на диск самого крупного экземпляра. Здесь помогает другой приём.

**Шардирование (sharding)** - разделение данных одной базы между несколькими независимыми серверами, каждый из которых хранит и обслуживает только свою часть строк[^8].

**Шард (shard)** - один из серверов шардированной базы вместе с частью данных, которую он хранит.

Все шарды имеют одинаковую схему, но разные строки. Каждый шард работает независимо и ничего не знает о других[^8].

Чтобы решить, в какой шард попадёт строка, выбирают ключ.

**Ключ шарда (shard key)** - столбец, по значению которого определяется, в каком шарде хранится строка[^8].

Для таблицы заказов удобный ключ шарда это `customer_id`: все заказы одного клиента окажутся в одном шарде, и запрос "заказы клиента 42" обратится только к нему.

### Типы шардирования

Ключ шарда говорит, по какому столбцу делить строки, но не говорит, как именно значение ключа превращается в номер шарда. От этого правила зависит тип шардирования. Основных типов четыре[^8]:

- _По диапазону (range-based)_. Строки делят по диапазонам значений ключа: клиенты с номерами от 1 до 1 000 000 попадают в первый шард, следующий миллион во второй.
- _По хешу (hashed)_. К значению ключа применяется хеш-функция, и её результат определяет номер шарда.
- _Географический (geo)_. Шард выбирают по местоположению пользователя: данные покупателей из Европы хранятся в одном шарде, из Америки в другом.

| Тип            | Преимущество                                                  | Недостаток                                                                                 |
| -------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| По диапазону   | Проще всего реализовать                                       | Нагрузка может скопиться в одном шарде: новые, самые активные клиенты окажутся в последнем |
| По хешу        | Данные распределяются по шардам равномерно                    | При добавлении шарда большинству строк нужно сменить шард                                  |
| Географический | Данные хранятся ближе к пользователю, поэтому запросы быстрее | Данные распределяются неравномерно: в одной стране покупателей больше, чем в другой        |

На рисунке 7.4 показано шардирование по хешу: таблица заказов разложена на три шарда по правилу `hash(customer_id) mod 3`. Номер шарда равен остатку от деления хеша на число шардов.

![Шардирование таблицы заказов по хешу customer_id](../_images/07/sharding.svg)

_7.4. Шардирование таблицы заказов по хешу `customer_id`_

У шардирования есть серьёзные недостатки, поэтому к нему прибегают, когда другие способы исчерпаны:

- _Горячий шард (hotspot)_. Если ключ выбран неудачно, большая часть запросов придётся на один шард, и он станет узким местом. _Например_, если на одного очень крупного клиента приходится половина всей нагрузки, его данные при любом типе шардирования окажутся в одном шарде.
- _Запросы через несколько шардов_. В схеме на рисунке 7.4 запрос "общая выручка за день" придётся отправить во все шарды и сложить результаты в приложении. Объединение таблиц из разных шардов тоже становится задачей приложения[^8].
- _Перераспределение данных_. При переходе с трёх шардов на четыре правило меняется на `hash(customer_id) mod 4`, и остаток от деления становится другим у большинства клиентов. Их заказы приходится переносить между серверами[^8].
- _Сложность эксплуатации_. Большинство реляционных СУБД не умеют шардировать данные сами, и эту логику пишут в приложении или в отдельном промежуточном слое[^8].

### Репликация и шардирование вместе

Репликацию и шардирование легко перепутать, потому что в обоих случаях данные лежат на нескольких серверах. Разница в том, что именно лежит на каждом сервере. Она показана на рисунке 7.5 и в таблице.

![Репликация, шардирование и их сочетание](../_images/07/replication_vs_sharding.svg)

_7.5. Репликация, шардирование и их сочетание_

| Свойство                    | Репликация                             | Шардирование                                  |
| --------------------------- | -------------------------------------- | --------------------------------------------- |
| Что на каждом сервере       | Полная копия одних и тех же данных     | Своя часть данных                             |
| Что масштабирует            | Чтение                                 | Запись и объём данных                         |
| Что даёт при отказе сервера | Реплика может заменить основной сервер | Без реплик часть данных становится недоступна |
| Основная сложность          | Задержка репликации                    | Выбор ключа и запросы через несколько шардов  |

На практике эти приёмы сочетают: базу делят на шарды, а у каждого шарда есть свои реплики[^8]. Тогда шарды распределяют запись, а реплики каждого шарда обеспечивают отказоустойчивость и чтение.

## Базы данных в облаке

### Своя СУБД или управляемый сервис

Все приёмы из предыдущего раздела можно настроить самостоятельно:

1. Запустить PostgreSQL на экземпляре EC2.
2. Настроить потоковую репликацию на второй экземпляр в другой зоне доступности.
3. Написать скрипт, который при отказе основного сервера переключит приложение на реплику.

Третий пункт сложнее, чем кажется. Документация PostgreSQL говорит, что сама СУБД не обнаруживает отказ основного сервера и не переключается автоматически: для этого нужны внешние инструменты[^9]. К этому добавляется повседневная работа администратора базы данных:

- обновления СУБД и операционной системы,
- резервные копии и проверка того, что они восстанавливаются,
- контроль свободного места на диске.

- _СУБД на экземпляре EC2 это IaaS_: AWS отвечает за сервер, а за операционную систему и всё, что выше неё, отвечаете вы.
- _Управляемая база данных это PaaS_: AWS запускает и обслуживает СУБД, а вы работаете с данными и доступом к ним.

| Задача                            | СУБД на EC2 | Управляемая база данных  |
| --------------------------------- | ----------- | ------------------------ |
| Установка и обновление СУБД и ОС  | Вы          | AWS                      |
| Резервное копирование             | Вы          | AWS, по вашим настройкам |
| Обнаружение отказа и переключение | Вы          | AWS                      |
| Увеличение диска                  | Вы          | AWS, по вашим настройкам |
| Схема и запросы                   | Вы          | Вы                       |
| Доступ к базе и сетевые правила   | Вы          | Вы                       |

За удобство приходится платить меньшей свободой. У управляемой базы есть ограничения:

- Нет доступа к операционной системе сервера.
- Нельзя поставить произвольное расширение СУБД.
- Выбор версий ограничен теми, что поддерживает провайдер.

Своя СУБД на EC2 оправдана, когда нужна такая свобода. В остальных случаях управляемая база экономит много работы.

### Базы данных AWS

AWS предлагает пятнадцать с лишним сервисов баз данных, каждый под свою модель данных[^10]. В этой главе мы подробно разберём четыре из них, а остальные упомянем коротко:

- _Amazon RDS_. Управляемые реляционные базы с привычными СУБД: PostgreSQL, MySQL и другими.
- _Amazon Aurora_. Реляционная база, совместимая с PostgreSQL и MySQL, с собственным распределённым хранилищем.
- _Amazon DynamoDB_. Нереляционная база для данных в виде пар ключ-значение и документов, без серверов, которыми нужно управлять.
- _Amazon Redshift_. Аналитическая база данных для отчётов по большим объёмам данных.

## Amazon RDS

### Что такое Amazon RDS

**Amazon RDS (Relational Database Service)** - управляемый сервис AWS, который упрощает создание, эксплуатацию и масштабирование реляционной базы данных в облаке[^11].

_Основные характеристики_ Amazon RDS:

- _Привычные СУБД_. RDS поддерживает шесть СУБД:
  - PostgreSQL,
  - MySQL,
  - MariaDB,
  - Microsoft SQL Server,
  - Oracle Database,
  - IBM Db2[^11].
- _Обслуживание берёт на себя AWS_. Резервное копирование, установка обновлений, обнаружение отказов и восстановление выполняются без вас, а на вашей стороне остаются схема базы и оптимизация запросов[^11].
- _Работа с экземплярами_. Как и в EC2, вы выбираете мощность сервера и размер диска, а платите за часы работы экземпляра.
- _Отказоустойчивость и масштабирование чтения_. Резервный экземпляр в другой зоне доступности и реплики для чтения включаются настройками экземпляра.
- _Восстановление на момент времени_. Базу можно вернуть в состояние на любую секунду в пределах срока хранения резервных копий.

AWS рекомендует RDS как выбор по умолчанию для большинства реляционных баз данных[^11].

| Характеристика      | Amazon RDS                                                                                                                       |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Категория           | Базы данных (databases)                                                                                                          |
| Что делает          | Запускает и обслуживает реляционную СУБД: обновления, резервные копии, мониторинг, переключение при отказе                       |
| Для чего нужен      | Получить готовую реляционную базу без администрирования сервера и СУБД                                                           |
| Где используют      | Основные данные веб-приложений: пользователи, заказы, платежи, учёт                                                              |
| Модель обслуживания | PaaS: серверами, ОС и СУБД управляет AWS, вы управляете схемой, данными и доступом                                               |
| Область действия    | Региональный: экземпляр базы находится в одной зоне доступности, копии могут быть в других зонах и регионах                      |
| Как оплачивается    | Часы работы экземпляра (по классу), объём хранилища в месяц, хранилище резервных копий сверх бесплатного объёма, передача данных |
| Как работать        | Консоль AWS, AWS CLI (`aws rds`), SDK; к самой базе подключаются обычным клиентом СУБД                                           |
| Появился            | Октябрь 2009 года[^12]                                                                                                           |
| Аналоги             | Google Cloud SQL[^13], Azure Database for PostgreSQL                                                                             |

### Экземпляр базы данных

Основной ресурс RDS называется экземпляром базы данных.

**Экземпляр базы данных (DB instance)** - изолированная среда базы данных в облаке, в которой работает одна СУБД с одной или несколькими базами[^11].

Экземпляр базы данных похож на экземпляр EC2, и при создании для него выбирают похожие параметры:

- _Класс экземпляра (DB instance class)_. Определяет процессор и память, как тип экземпляра в EC2. Имена классов начинаются с `db.`, дальше идут знакомые семейство, поколение и размер, например `db.t4g.micro` или `db.r6g.xlarge`. Классы `db.t` рассчитаны на небольшую нагрузку с редкими пиками, `db.m` сбалансированы, `db.r` оптимизированы по памяти[^14].
- _Хранилище_. Том EBS, на котором лежат файлы базы. Обычный выбор это General Purpose SSD `gp3`, для нагрузок с высокими требованиями к скорости дисковых операций есть Provisioned IOPS SSD (`io1`, `io2`)[^15].
- _Автоматическое увеличение хранилища (storage autoscaling)_. Если свободного места почти не осталось, RDS сам увеличит том, но не выше заданного вами максимума[^16].
- _Учётные данные администратора_. Имя главного пользователя (master user) и пароль, с которыми вы подключаетесь к базе.

> [!TIP]
>
> Подключаться к экземпляру по SSH нельзя: RDS не даёт прямого доступа к серверу, на котором работает СУБД[^17]. Вы работаете только с самой базой через клиент СУБД.

### Подключение к экземпляру

Каждый экземпляр получает адрес для подключения.

**Endpoint экземпляра (DB instance endpoint)** - DNS-имя, по которому приложение подключается к экземпляру базы данных[^17]. Endpoint выглядит так: `shop-db.abcdefghijkl.eu-central-1.rds.amazonaws.com`. Приложение подключается по этому имени, а не по IP-адресу.

### RDS в VPC

Экземпляр базы данных всегда создаётся внутри VPC. Все концепции, которые были изучены в главе про VPC, применимы и к RDS. При создании экземпляра нужно указать, в каких подсетях он может работать.

**Группа подсетей базы данных (DB subnet group)** - набор подсетей VPC, обычно приватных, в которых RDS может размещать экземпляры базы данных[^18].

Экземпляр один и работает в одной подсети. Группа только перечисляет подсети, в которых RDS разрешено его разместить, а конкретную подсеть RDS выбирает сам[^18].

Зачем тогда несколько подсетей? AWS требует, чтобы подсети группы находились как минимум в двух зонах доступности[^18]. Вторая зона нужна в двух случаях:

- при включении режима Multi-AZ туда помещают резервный экземпляр,
- при отказе основного экземпляра RDS создаёт новый резервный экземпляр в одной из других зон[^18].

Ещё два параметра определяют, кто сможет подключиться к базе:

- _Public access_. Параметр определяет, получит ли экземпляр публичный IP-адрес. Для базы приложения выбирают `No`: база доступна только изнутри VPC[^18].
- _Security Group_. Окончательное решение о доступе принимают правила Security Group экземпляра[^18].

> [_Hands-on 7.1. Первая база данных в RDS._](hands_on_01.md) Создание группы подсетей из двух приватных подсетей, запуск экземпляра PostgreSQL.

### Multi-AZ: защита от отказа зоны

Экземпляр базы данных работает в одной зоне доступности. Если в этой зоне откажет сервер, сеть или диск, база станет недоступна, а вместе с ней и весь магазин.

Решение мы уже знаем из подраздела ["Репликация в базах данных"](#репликация-в-базах-данных): держать реплику в другой зоне и при отказе основного сервера переключиться на неё. В RDS это включается одной настройкой.

**Развёртывание Multi-AZ (Multi-AZ DB instance deployment)** - режим RDS, в котором AWS создаёт в другой зоне доступности резервный экземпляр (standby) и синхронно копирует на него все изменения основного экземпляра[^19].

Это схема с одним основным сервером и одной синхронной репликой, а переключение при отказе AWS выполняет сам. Масштабированием этот режим не является: резервный экземпляр не принимает ни запись, ни чтение, он только ждёт отказа основного[^19].

На рисунке 7.6 показана работа в этом режиме:

- Приложение читает и пишет только в основной экземпляр (Primary DB instance).
- Каждая запись синхронно копируется на резервный экземпляр (Standby replica) в другой зоне.
- Если основной экземпляр или его зона отказали, RDS сам переключается на резервный экземпляр, и приложение продолжает работу уже с ним[^20].

![Развёртывание Multi-AZ: основной и резервный экземпляры в разных зонах](../_images/07/rds_multi_az.png)

_7.6. Развёртывание Multi-AZ: основной и резервный экземпляры в разных зонах. Источник: Amazon Web Services[^19], лицензия CC BY-SA 4.0[^21]_

Переключение обычно занимает 60-120 секунд[^20]. Репликация синхронная, поэтому подтверждённые транзакции при переключении не теряются.

За надёжность приходится платить:

- _Запись становится медленнее_. Каждая транзакция ждёт подтверждения из другой зоны[^19].
- _Режим стоит дороже_. Резервный экземпляр работает круглосуточно, а RDS оплачивается по часам работы экземпляров[^22].

> [!NOTE]
>
> Multi-AZ защищает от отказа оборудования и зоны, но не от ошибок. Если приложение удалит таблицу, синхронная репликация тут же удалит её и на резервном экземпляре.

### Реплики для чтения в RDS

Multi-AZ отвечает за отказоустойчивость, а для масштабирования чтения в RDS есть реплики для чтения.

Реплика для чтения в RDS это отдельный экземпляр базы данных со своим отдельным endpoint. RDS копирует на неё изменения основного экземпляра асинхронно[^23]. Разработчик сам указывает какие запросы отправлять на endpoint реплики: RDS не распределяет запросы автоматически.

Основные свойства реплик для чтения в RDS:

- _Количество_. К одному экземпляру можно подключить до 15 реплик, а для Oracle до 5[^24][^23].
- _Размещение_. Реплика может находиться в той же зоне, в другой зоне или даже в другом регионе[^23]. Реплика в другом регионе приближает данные к пользователям и служит запасом на случай отказа региона.
- _Продвижение (promotion)_. Реплику можно превратить в самостоятельный экземпляр, принимающий запись. Так её используют для восстановления после аварии, если основной экземпляр потерян[^23].
- _Ручное создание_. RDS не добавляет реплики автоматически при росте нагрузки, их создают вручную[^23].

Multi-AZ и реплики для чтения можно сочетать. На рисунке 7.7 у основного экземпляра есть и синхронный резервный экземпляр без доступа на чтение, и асинхронная реплика, с которой клиенты читают данные (Read access).

![Основной экземпляр с резервным экземпляром Multi-AZ и репликой для чтения](../_images/07/rds_read_and_standby_replica.png)

_7.7. Основной экземпляр с резервным экземпляром Multi-AZ и репликой для чтения. Источник: Amazon Web Services[^23], лицензия CC BY-SA 4.0[^21]_

Multi-AZ и реплики для чтения решают разные задачи, и их часто путают.

| Свойство                | Multi-AZ                                   | Реплика для чтения                        |
| ----------------------- | ------------------------------------------ | ----------------------------------------- |
| Назначение              | Отказоустойчивость                         | Масштабирование чтения                    |
| Репликация              | Синхронная                                 | Асинхронная                               |
| Обслуживает чтение      | Нет                                        | Да                                        |
| Отдельный endpoint      | Нет, endpoint общий с основным экземпляром | Да                                        |
| Где находится           | Другая зона того же региона                | Та же зона, другая зона или другой регион |
| Переключение при отказе | Автоматическое                             | Ручное продвижение                        |

### Резервные копии и восстановление

От ошибок защищают резервные копии. Они хранятся в Amazon S3 и бывают двух видов[^25]:

- _Автоматические резервные копии (automated backups)_. RDS каждый день в заданный промежуток времени делает снимок хранилища экземпляра, а журналы транзакций выгружает каждые пять минут. Срок хранения задают от 0 до 35 дней, значение 0 отключает автоматическое резервное копирование.
- _Ручные снимки (manual snapshots)_. Их делаете вы, например перед обновлением схемы базы. Ручной снимок хранится, пока его не удалят явно, даже если сам экземпляр уже удалён[^26].

Благодаря журналам транзакций автоматические копии позволяют вернуться не только к ежедневному снимку, но и к любому моменту между снимками.

**Восстановление на момент времени (point-in-time recovery)** - восстановление базы в состояние на выбранную секунду в пределах срока хранения резервных копий.

Восстановление устроено в два шага:

1. RDS берёт последний ежедневный снимок, сделанный до выбранного момента.
2. RDS заново применяет к этому снимку изменения из журналов транзакций вплоть до выбранной секунды.

Например, администратор по ошибке удалил таблицу заказов в 14:37. Базу восстанавливают на 14:36, за минуту до ошибки.

> [!NOTE]
>
> Восстановление не перезаписывает существующую базу: RDS создаёт новый экземпляр[^27]. Чтобы приложение начало работать с восстановленной базой, в его настройках указывают endpoint нового экземпляра.

### Обслуживание экземпляра

Обновления СУБД и операционной системы RDS устанавливает сам, но некоторые из них требуют короткой остановки экземпляра. Чтобы это не случилось в разгар продаж, для экземпляра задают окно обслуживания.

**Окно обслуживания (maintenance window)** - еженедельный интервал времени, в который RDS применяет к экземпляру изменения, требующие его остановки, например обновления ОС или СУБД[^28].

Для магазина окно обычно ставят на ночь, когда покупателей меньше всего. В режиме Multi-AZ обновление ОС проходит почти без простоя, потому что RDS действует по шагам[^28]:

1. Обновляет резервный экземпляр.
2. Делает его основным.
3. Обновляет бывший основной экземпляр, который становится резервным.

### Стоимость RDS

Счёт за RDS складывается из нескольких частей[^22]:

| Что оплачивается | Как считается                                                          | Что важно помнить                                              |
| ---------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------- |
| Экземпляр        | Часы работы, цена зависит от класса экземпляра и СУБД                  | Экземпляр оплачивается, даже если к нему никто не подключается |
| Хранилище        | Выделенный объём в месяц, для Provisioned IOPS ещё и заданная скорость | Платят за выделенный, а не за занятый объём                    |
| Резервные копии  | Объём копий сверх бесплатного                                          | Бесплатно в объёме выделенного хранилища баз в регионе[^26]    |
| Передача данных  | Трафик в интернет и между регионами                                    | Репликация на реплику в том же регионе бесплатна[^23]          |

Режим Multi-AZ и каждая реплика для чтения добавляют часы работы ещё одного экземпляра. Поэтому для учебных задач используют один экземпляр в одной зоне.

## Amazon Aurora

### Зачем понадобилась Aurora

Если говорить о RDS, то у каждого экземпляра свой том с файлами базы:

- у основного,
- у резервного экземпляра Multi-AZ,
- у каждой реплики для чтения.

Основной экземпляр отправляет каждое изменение на все эти тома. Чем больше реплик, тем больше копий данных нужно поддерживать и тем дольше создаётся новая реплика: ей нужно получить полную копию базы.

AWS решила эту проблему иначе: отделила хранилище от вычислений. Так появилась _Aurora_.

### Что такое Amazon Aurora

**Amazon Aurora** - полностью управляемая реляционная СУБД, совместимая с MySQL и PostgreSQL, в которой данные хранятся в общем распределённом томе, отделённом от серверов СУБД[^29].

_Основные характеристики_ Amazon Aurora:

- _Совместимость с MySQL и PostgreSQL_. Приложение работает с Aurora через тот же драйвер и с теми же запросами.
- _Общее хранилище в трёх зонах_. Данные хранятся в шести копиях, по две в каждой из трёх зон доступности[^30][^31].
- _До 15 реплик для чтения_. Реплики читают то же общее хранилище и своих копий данных не держат[^32].
- _Быстрая замена основного экземпляра_. При отказе одна из реплик становится основным экземпляром, и данные копировать не нужно[^32].

| Характеристика      | Amazon Aurora                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| Категория           | Базы данных (databases)                                                                                       |
| Что делает          | Запускает реляционную СУБД, совместимую с MySQL или PostgreSQL, над общим томом с копиями данных в трёх зонах |
| Для чего нужен      | Реляционная база с высокой доступностью и быстрыми репликами для нагруженных приложений                       |
| Где используют      | Нагруженные веб-приложения и SaaS-сервисы, системы, где важна быстрая замена основного сервера                |
| Модель обслуживания | PaaS                                                                                                          |
| Область действия    | Региональный: общий том охватывает три зоны доступности региона                                               |
| Как оплачивается    | Часы работы экземпляров, объём хранилища, операции ввода-вывода (зависит от конфигурации), резервные копии    |
| Как работать        | Те же консоль и команды `aws rds`, что для RDS; к базе подключаются клиентом MySQL или PostgreSQL             |
| Появился            | Анонс в ноябре 2014 года, общая доступность в июле 2015 года[^33][^34]                                        |
| Аналоги             | Google Cloud AlloyDB for PostgreSQL[^35]                                                                      |

### Как устроена Aurora

**Кластер Aurora (Aurora DB cluster)** - один или несколько экземпляров базы данных вместе с общим томом, на котором лежат данные для всех этих экземпляров[^29].

В кластере экземпляры делят работу так:

- _Основной экземпляр (writer)_. Он один и принимает запись.
- _Реплики (readers)_. Они только читают данные из того же общего тома, что и основной экземпляр[^32].

На рисунке 7.8 основной экземпляр (Writer instance) находится в первой зоне, реплики (Reader instances) во второй и третьей, а под ними лежит общий том (Shared storage volume) с копиями данных во всех трёх зонах.

![Кластер Aurora: экземпляры над общим томом в трёх зонах доступности](../_images/07/aurora_architecture.png)

_7.8. Кластер Aurora: экземпляры над общим томом в трёх зонах доступности. Источник: Amazon Web Services[^36], лицензия CC BY-SA 4.0[^21]_

Отличие от RDS в том, что данные лежат в одном месте, а не на томе каждого экземпляра. Поэтому новой реплике не нужно копировать базу, а при отказе основного экземпляра одна из реплик сразу становится основной[^32].

### RDS или Aurora

Aurora не всегда лучше обычного RDS.

| Ситуация                                                           | Что выбрать         | Почему                                                 |
| ------------------------------------------------------------------ | ------------------- | ------------------------------------------------------ |
| Небольшая база, учебный проект                                     | RDS, один экземпляр | Проще и не нужно платить за лишние возможности         |
| Нужна СУБД, которой нет в Aurora: Oracle, SQL Server, Db2, MariaDB | RDS                 | Aurora совместима только с MySQL и PostgreSQL          |
| Много чтения, нужно много реплик                                   | Aurora              | Реплики читают общий том и не копируют базу            |
| Важна быстрая замена основного сервера                             | Aurora              | Новому основному экземпляру не нужно копировать данные |

## Amazon DynamoDB

### Зачем нужна DynamoDB

Вернёмся к корзине покупателя. Корзину читают и меняют при каждом добавлении товара и каждом открытии страницы. Обращаются к ней всегда по одному ключу, идентификатору покупателя, и никогда не объединяют с другими таблицами. В распродажу число таких запросов может вырасти в сотни раз за минуты.

Реляционная база с этим справится, но её придётся заранее подбирать под пик нагрузки и платить за неё круглый год. Кроме того, вся запись идёт через один основной сервер. Для таких данных лучше подходит база ключ-значение, которая масштабируется горизонтально без вашего участия.

### Что такое DynamoDB

**Amazon DynamoDB** - полностью управляемая распределённая NoSQL-база данных AWS, поддерживающая модель ключ-значение и документную модель[^37].

_Основные характеристики_ Amazon DynamoDB:

- _Ключ-значение и документы_. Элемент находят по ключу, а внутри элемента могут быть вложенные поля, как в JSON[^37].
- _Автоматическое горизонтальное масштабирование_. DynamoDB сама делит данные таблицы между серверами и добавляет новые по мере роста.
- _Три зоны доступности_. DynamoDB сама копирует данные каждой таблицы в три зоны доступности региона[^37].
- _Гибкая схема_. При создании таблицы задают только первичный ключ, остальные атрибуты у каждого элемента свои.

| Характеристика      | Amazon DynamoDB                                                                                                         |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Категория           | Базы данных (databases)                                                                                                 |
| Что делает          | Хранит элементы в таблицах и выдаёт их по ключу с задержкой в несколько миллисекунд при любом объёме                    |
| Для чего нужен      | Хранить данные, к которым обращаются по ключу, с горизонтальным масштабированием без управления серверами               |
| Где используют      | Корзины и сессии, профили пользователей, игровые данные, счётчики, журналы событий                                      |
| Модель обслуживания | PaaS: серверов нет, вы управляете таблицами, данными и доступом                                                         |
| Область действия    | Региональный: данные таблицы копируются в три зоны доступности региона                                                  |
| Как оплачивается    | Запросы на чтение и запись (или заранее заданная пропускная способность), объём хранения, дополнительные функции        |
| Как работать        | Консоль AWS, AWS CLI (`aws dynamodb`), SDK (для JavaScript пакеты `@aws-sdk/client-dynamodb` и `@aws-sdk/lib-dynamodb`) |
| Появился            | Январь 2012 года[^38]                                                                                                   |
| Аналоги             | Google Cloud Firestore[^39] и Bigtable[^40], Azure Cosmos DB                                                            |

### Таблицы, элементы и атрибуты

- _Таблица (table)_. Набор элементов, например таблица `Carts` с корзинами.
- _Элемент (item)_. Одна запись таблицы, аналог строки в реляционной таблице.
- _Атрибут (attribute)_. Отдельное значение внутри элемента, например `quantity`. Аналог столбца, но набор атрибутов у элементов одной таблицы может различаться.

Например, у одного элемента таблицы `Carts` есть атрибут `size`, у другого `color`, и таблицу для этого менять не нужно:

```json
[
  { "userId": "u-42", "productId": "p-7", "quantity": 2, "size": "L" },
  { "userId": "u-42", "productId": "p-9", "quantity": 1, "color": "red" }
]
```

Размер одного элемента ограничен 400 КБ[^42], поэтому большие данные, например фотографии, хранят в S3, а в элементе только ключ объекта.

### Первичный ключ и разделы

Первичный ключ в DynamoDB определяет не только уникальность элемента, но и то, где элемент физически хранится. Здесь мы снова встречаем _шардирование_, только выполняет его сама DynamoDB.

**Раздел (partition)** - часть хранилища таблицы DynamoDB, которая автоматически копируется в несколько зон доступности. Разделами управляет DynamoDB, вы их не видите и не настраиваете[^43].

**Ключ раздела (partition key)** - первичный ключ, значение которого DynamoDB пропускает через внутреннюю хеш-функцию. Результат хеш-функции определяет раздел, в котором хранится элемент[^43].

- Раздел DynamoDB это шард,
- Ключ раздела это ключ шарда при шардировании по хешу.

Ключ раздела может дополняться вторым атрибутом.

**Ключ сортировки (sort key)** - второй атрибут составного первичного ключа. Элементы с одинаковым ключом раздела хранятся вместе и упорядочены по значению ключа сортировки[^41].

Рассмотрим пример.

- В таблице `Carts` каждый элемент описывает один товар в корзине одного покупателя.
- Ключом раздела служит `userId`, ключом сортировки `productId`.

Все товары корзины одного покупателя лежат в одном разделе рядом друг с другом (рисунок 7.9), и вся корзина читается одним запросом.

![Хеш ключа раздела userId определяет раздел, в котором хранятся элементы корзины](../_images/07/dynamodb_partitions.svg)

_7.9. Хеш ключа раздела `userId` определяет раздел, в котором хранятся элементы корзины_

### Выбор ключа раздела

Неудачный ключ раздела создаёт ту же проблему горячего шарда. Если большая часть запросов относится к одному значению ключа, все они попадают в один раздел. Тогда DynamoDB начинает отвечать на часть запросов ошибкой о превышении пропускной способности (throttling), и приложению приходится повторять запрос позже[^44].

| Ключ раздела                                               | Оценка и причина                                                |
| ---------------------------------------------------------- | --------------------------------------------------------------- |
| Идентификатор пользователя при большом числе пользователей | Хороший: много разных значений, запросы распределены равномерно |
| Код статуса, у которого всего несколько значений           | Плохой: почти все запросы приходятся на несколько разделов      |
| Дата создания, округлённая до дня                          | Плохой: все записи текущего дня попадают в один раздел          |

### Чтение: Query и Scan

Получить данные из таблицы DynamoDB можно тремя основными операциями:

- _GetItem_. Читает один элемент по полному первичному ключу.
- _Query_. Находит элементы с одним значением ключа раздела и, при необходимости, отбирает их по условию на ключ сортировки[^45].
- _Scan_. Читает всю таблицу целиком и проверяет каждый элемент[^46].

Чтобы получить корзину покупателя `u-42`, нужен Query по `userId = "u-42"`. Тот же результат можно получить через Scan с фильтром, но Scan прочитает все корзины всех покупателей, и платить придётся за весь прочитанный объём. Поэтому AWS рекомендует проектировать таблицы так, чтобы приложение использовало _Query вместо Scan_[^46].

В PostgreSQL можно написать любой запрос, и СУБД найдёт способ его выполнить. В DynamoDB быстро выполняются только запросы по ключу, поэтому сначала составляют список запросов приложения, а потом под них выбирают ключи таблицы.

Если нужен запрос по другому атрибуту, например все корзины с определённым товаром, создают дополнительную копию данных с другим ключом.

**Глобальный вторичный индекс (global secondary index, GSI)** - копия выбранных атрибутов таблицы DynamoDB, разложенная по другому ключу раздела. DynamoDB обновляет её автоматически при каждом изменении таблицы, и по ней можно выполнять Query[^47].

Например, индекс с ключом раздела `productId` позволит найти все корзины с товаром `p-7`. Хранение индекса и запись в него оплачиваются отдельно[^47].

### Согласованность чтения

DynamoDB хранит копии каждого раздела в нескольких зонах доступности, и после записи изменение доходит до всех копий не мгновенно. Это та же задержка репликации, что и у реплик для чтения. Поэтому DynamoDB предлагает два режима чтения[^48]:

- _Согласованное в конечном счёте чтение (eventually consistent read)_. Режим по умолчанию. Чтение может не увидеть только что выполненную запись, но стоит вдвое дешевле строго согласованного.
- _Строго согласованное чтение (strongly consistent read)_. Включается параметром `ConsistentRead: true` и возвращает самые свежие данные.

Если пользователь добавил товар и сразу открывает корзину, чтение корзины делают строго согласованным, иначе он может не увидеть товар, который только что положил.

### Режимы ёмкости и стоимость

DynamoDB оплачивается не за серверы, а за:

- запросы,
- хранение.

Способ оплаты запросов задаётся режимом ёмкости таблицы[^49]:

| Режим                          | Как платите                                                         | Когда подходит                                     |
| ------------------------------ | ------------------------------------------------------------------- | -------------------------------------------------- |
| По запросам (on-demand)        | За каждый выполненный запрос на чтение и запись                     | Режим по умолчанию, нагрузка неизвестна или скачет |
| Заданная ёмкость (provisioned) | За заданное число операций в секунду, даже если они не используются | Предсказуемая ровная нагрузка                      |

Бесплатный уровень DynamoDB включает 25 ГБ хранения в обоих режимах. Небольшая ёмкость, 25 единиц чтения и 25 единиц записи, бесплатна только в режиме заданной ёмкости[^50]. Поэтому учебную таблицу создают в режиме заданной ёмкости с небольшими значениями.

### Работа с DynamoDB из Node.js

С DynamoDB приложение работает через AWS SDK. Для JavaScript удобнее всего пакет `@aws-sdk/lib-dynamodb` с клиентом документов (document client), который принимает обычные объекты JavaScript[^51]. Ниже показаны добавление товара в корзину и чтение всей корзины покупателя:

```javascript
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import {
  DynamoDBDocumentClient,
  PutCommand,
  QueryCommand,
} from "@aws-sdk/lib-dynamodb";

const client = new DynamoDBClient({ region: "eu-central-1" });
const docClient = DynamoDBDocumentClient.from(client);

// Добавить товар в корзину покупателя u-42
await docClient.send(
  new PutCommand({
    TableName: "Carts",
    Item: { userId: "u-42", productId: "p-7", quantity: 2 },
  }),
);

// Прочитать всю корзину покупателя u-42 одним запросом Query
const result = await docClient.send(
  new QueryCommand({
    TableName: "Carts",
    KeyConditionExpression: "userId = :uid",
    ExpressionAttributeValues: { ":uid": "u-42" },
  }),
);
console.log(result.Items);
```

`PutCommand` записывает элемент: если элемент с таким же первичным ключом уже есть, он будет заменён. `QueryCommand` принимает условие на ключ раздела в параметре `KeyConditionExpression`. Если корзина была пустой, программа выведет:

```text
[ { userId: 'u-42', productId: 'p-7', quantity: 2 } ]
```

> [_Hands-on 7.2. Таблица DynamoDB._](hands_on_02.md) Создание таблицы `Carts` с ключом раздела и ключом сортировки, запись и чтение элементов, сравнение Query и Scan.

### Дополнительные возможности DynamoDB

- _Время жизни (time to live, TTL)_. Если указать атрибут со временем истечения, DynamoDB сама удалит просроченные элементы, обычно в течение нескольких дней после срока[^52]. Так удаляют брошенные корзины и старые сессии.
- _Потоки (DynamoDB Streams)_. Журнал изменений элементов таблицы, по которому другие части системы узнают об этих изменениях[^53].
- _Глобальные таблицы (global tables)_. Копии таблицы в нескольких регионах, каждая из которых принимает запись[^54].
- _Транзакции_. Изменения нескольких элементов можно выполнить как одно целое[^37].

### DynamoDB или RDS

| Свойство        | Amazon RDS                                | Amazon DynamoDB                             |
| --------------- | ----------------------------------------- | ------------------------------------------- |
| Модель данных   | Таблицы со схемой, связи между таблицами  | Элементы с гибким набором атрибутов         |
| Запросы         | Любые запросы на SQL, `JOIN`              | По ключу, Query по ключу раздела, GSI       |
| Масштабирование | Вертикальное, реплики для чтения          | Горизонтальное, автоматическое              |
| Серверы         | Вы выбираете класс экземпляра             | Серверов нет                                |
| Оплата          | Часы работы экземпляра, даже без запросов | Запросы и объём хранения                    |
| Подходит для    | Заказы, платежи, учёт, сложные отчёты     | Корзины, сессии, профили, счётчики, события |

Если запросы к данным заранее неизвестны или нужны связи между таблицами, начинают с реляционной базы. DynamoDB выбирают, когда:

- список запросов известен заранее,
- обращения идут по ключу,
- нагрузка велика или непредсказуема.

## Amazon Redshift и аналитика

### Аналитические запросы на рабочей базе

Менеджер магазина просит отчёт о выручке по категориям товаров за каждый месяц прошлого года. Запрос для такого отчёта читает миллионы строк заказов, но только несколько столбцов: дату, категорию и сумму. Если выполнить его на основной базе магазина, он надолго загрузит сервер, и покупатели почувствуют замедление.

Реплика для чтения снимет нагрузку с основного сервера, но не сделает сам запрос быстрее: реплика хранит данные так же, как основной сервер, и прочитает миллионы заказов вместе со всеми их столбцами. Для таких запросов нужна другая организация хранения.

### OLTP и OLAP

Базы данных решают два разных вида задач[^55]:

- _OLTP (online transaction processing)_. Множество коротких запросов, каждый из которых читает или меняет несколько строк: оформление заказа, изменение корзины, вход пользователя. Для этого предназначены RDS, Aurora и DynamoDB.
- _OLAP (online analytical processing)_. Немного длинных запросов, каждый из которых читает и группирует огромное число строк: отчёты, анализ продаж, поиск закономерностей.

**Хранилище данных (data warehouse)** - база данных для аналитики, в которую данные регулярно загружаются из рабочих баз и других источников и которая оптимизирована под запросы, читающие большие объёмы данных.

Не путайте хранилище данных с хранилищем файлов вроде S3: название похоже, но это база данных для аналитических запросов на SQL.

### Amazon Redshift

**Amazon Redshift** - полностью управляемое хранилище данных AWS для аналитических запросов на SQL к данным объёмом до петабайтов[^56].

_Основные характеристики_ Amazon Redshift:

- _SQL_. Запросы пишут на SQL, а его диалект в Redshift основан на PostgreSQL[^57].
- _Хранение по столбцам_. Запрос читает с диска только нужные ему столбцы[^58].
- _Параллельная обработка_. Один запрос выполняется одновременно на нескольких узлах[^59].
- _Пакетная загрузка (batch loading)_. Данные загружают не построчно в момент покупки, а большими порциями из рабочих баз и файлов, например раз в сутки[^60].

| Характеристика      | Amazon Redshift                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Категория           | Аналитика (analytics)                                                                                              |
| Что делает          | Хранит большие объёмы данных и быстро выполняет аналитические SQL-запросы к ним                                    |
| Для чего нужен      | Отчёты и анализ данных без нагрузки на рабочие базы приложения                                                     |
| Где используют      | Отчёты о продажах, анализ поведения пользователей                                                                  |
| Модель обслуживания | PaaS                                                                                                               |
| Область действия    | Региональный                                                                                                       |
| Как оплачивается    | Кластер: часы работы узлов. Redshift Serverless: вычисления во время выполнения запросов. Отдельно хранение данных |
| Как работать        | Консоль AWS, AWS CLI, SQL-клиенты                                                                                  |
| Появился            | Ноябрь 2012 года, ограниченная бета-версия[^61]                                                                    |
| Аналоги             | Google BigQuery[^62], Azure Synapse Analytics                                                                      |

### Хранение по столбцам

**Колоночное хранение (columnar storage)** - способ хранения таблицы, при котором значения одного столбца для многих строк записываются на диск рядом, в одни и те же блоки[^58].

## Резюме

1. Хранилище отдаёт файлы и объекты по ключу, а база данных ищет записи по содержимому, меняет отдельные поля и согласует одновременные изменения.
2. Реляционные базы хранят данные в таблицах со схемой, поддерживают SQL и транзакции и обычно масштабируются вертикально. Нереляционные базы выбирают модель данных под задачу и масштабируются горизонтально, но запросы к ним приходится проектировать заранее.
3. Репликация копирует изменения основного сервера на реплики. Синхронная не теряет подтверждённых данных, но замедляет запись, асинхронная быстрее, но при отказе теряет последние изменения.
4. Реплики для чтения разгружают основной сервер, но из-за задержки репликации могут показывать устаревшие данные. Запись они не ускоряют.
5. Шардирование делит данные между независимыми серверами по ключу шарда. Различают шардирование по диапазону, по хешу, по справочнику и географическое. Неудачный ключ создаёт горячий шард.
6. Amazon RDS запускает PostgreSQL, MySQL и другие СУБД как управляемый сервис. Экземпляр размещают в приватных подсетях через группу подсетей минимум из двух зон.
7. Multi-AZ держит синхронный резервный экземпляр в другой зоне и переключается на него автоматически, а реплики для чтения асинхронные и обслуживают чтение. Резервные копии позволяют восстановить базу на любую секунду в пределах срока хранения.
8. Aurora отделяет хранилище от вычислений: все экземпляры кластера работают с одним общим томом, поэтому реплики не копируют базу.
9. DynamoDB это бессерверная база ключ-значение. Ключ раздела через хеш определяет раздел, поэтому значений у ключа должно быть много, и обращаться к ним нужно примерно одинаково часто. Запросы к таблице делают через Query, а не Scan.
10. Redshift это хранилище данных для аналитики с колоночным хранением и параллельной обработкой. Его используют для отчётов, а не как основную базу приложения.
