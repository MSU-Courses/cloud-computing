# Hands-on 8.1. Балансировщик для двух серверов

В этом занятии вы настроите Application Load Balancer для двух веб-серверов. Оба сервера будут принимать запросы через один адрес. Затем вы остановите один из них и проверите, продолжит ли сайт работать.

После основных настроек мы коротко разберём, зачем они нужны и как влияют на работу системы.

## Что получится в конце

- Две Security Group: `alb-sg` принимает HTTP-запросы из интернета, а `web-sg` разрешает доступ к серверам только от балансировщика.
- Два экземпляра EC2: `web-1` в зоне `eu-central-1a` и `web-2` в `eu-central-1b`, оба с nginx.
- Целевая группа `web-tg`, которая проверяет доступность серверов по пути `/health`.
- Внешний Application Load Balancer `web-alb` с HTTP-listener на порту 80.

Все ресурсы создадим в default VPC. В ней уже есть публичные подсети, поэтому новую сеть настраивать не потребуется.

| Зона доступности | Подсеть default VPC | Ресурсы                           |
| ---------------- | ------------------- | --------------------------------- |
| `eu-central-1a`  | `172.31.16.0/20`    | Узел `web-alb`, экземпляр `web-1` |
| `eu-central-1b`  | `172.31.32.0/20`    | Узел `web-alb`, экземпляр `web-2` |

Адреса подсетей приведены для примера. В вашем аккаунте они могут быть другими.

## Перед началом

- Вы умеете запускать EC2 с `User data` и создавать Security Group (Hands-on 4.1 и 5.1).
- Выбран регион `Europe (Frankfurt)`.
- На занятие понадобится около часа.

> [!WARNING]
> Балансировщик оплачивается всё время, пока существует, даже если запросов нет. Публичные IPv4-адреса тоже стоят денег. Если не переходите сразу к Hands-on 8.2, в конце выполните часть 5 и удалите ресурсы.

## Часть 1. Security Group и серверы

### Шаг 1. Создайте Security Group балансировщика

Откройте `EC2` → `Security Groups` → `Create security group`. Укажите:

- `Security group name`: `alb-sg`.
- `Description`: `HTTP from the internet`.
- `VPC`: default VPC.
- Входящее правило: `HTTP`, источник `Anywhere-IPv4` (`0.0.0.0/0`).

Нажмите `Create security group`. Теперь балансировщик сможет принимать HTTP-запросы из интернета через порт 80. HTTPS (порт 443) в этом занятии не настраиваем.

> [!NOTE]
> В примерах главы встречаются имена `sg-alb` и `sg-web`. Для реальных Security Group мы используем `alb-sg` и `web-sg`: AWS не разрешает начинать имя группы с `sg-`, поскольку так начинаются их идентификаторы.

### Шаг 2. Создайте Security Group серверов

Создайте ещё одну Security Group для веб-серверов:

1. Введите `web-sg` в `Security group name` (_1_), а `HTTP only from load balancer` - в `Description`.
2. Добавьте входящее правило `HTTP` (_2_). Порт 80 будет выбран автоматически.
3. В `Source` найдите и выберите группу `alb-sg` (_3_). В поле появится идентификатор `sg-...`. При желании добавьте описание `From ALB`.

Нажмите `Create security group`.

![8.1.1. Security Group серверов](../_images/08/hands_on/ho1_01_web_sg.jpg)

_8.1.1. Security Group серверов_

Мы указали источником не IP-адрес, а группу `alb-sg`. Это значит, что веб-серверы принимают HTTP-запросы только от балансировщика. Даже если IP-адреса его узлов изменятся, правило продолжит работать.

> [!WARNING]
> В поле `Source` нужно выбрать `alb-sg` из списка, а не просто напечатать её имя. Иначе консоль может показать ошибку.

### Шаг 3. Запустите два экземпляра

Откройте `Instances` → `Launch instances`. Укажите имя `web-1`, образ Amazon Linux 2023 и тип `t3.micro`. Для `Key pair` выберите `Proceed without a key pair (Not recommended)`: SSH нам не понадобится.

В `Network settings` нажмите `Edit` и настройте сеть:

1. `VPC`: default VPC (_4_).
2. `Subnet`: подсеть в `eu-central-1a` (_5_). Не оставляйте `No preference`, иначе оба сервера могут оказаться в одной зоне.
3. `Auto-assign public IP`: `Enable` (_6_). При запуске сервер должен получить доступ к репозиторию, чтобы установить nginx.
4. `Firewall (security groups)`: `Select existing security group` → `web-sg` (_7_).

![8.1.2. Сетевые настройки экземпляра web-1](../_images/08/hands_on/ho1_02_web1_network.jpg)

_8.1.2. Сетевые настройки экземпляра web-1_

У сервера будет публичный IP-адрес, но открыть по нему сайт напрямую не получится: это запрещает `web-sg`. Позже мы проверим это.

Откройте `Advanced details`. В поле `User data` вставьте скрипт (_8_):

```bash
#!/bin/bash
dnf install -y nginx
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
AZ=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone)
echo "<h1>$(hostname)</h1><p>Zone: $AZ</p>" > /usr/share/nginx/html/index.html
echo "OK" > /usr/share/nginx/html/health
systemctl enable --now nginx
```

![8.1.3. User data веб-сервера](../_images/08/hands_on/ho1_03_userdata.jpg)

_8.1.3. User data веб-сервера_

При запуске скрипт установит nginx и создаст две страницы:

- _Главная страница `/`_. Покажет имя сервера и его зону доступности. Скрипт получает зону через Instance Metadata Service с токеном IMDSv2. По ответу будет видно, какой сервер обработал запрос.
- _Страница `/health`_ (_9_). Содержит текст `OK`. Когда nginx работает, он возвращает для неё HTTP-код 200. Балансировщик будет использовать этот адрес для проверки сервера.

Нажмите `Launch instance`. Затем создайте `web-2` с теми же параметрами, но выберите подсеть в `eu-central-1b`.

Можно ускорить настройку: выберите `web-1` в списке экземпляров и откройте `Actions` → `Image and templates` → `Launch more like this`. Измените только имя и подсеть. Убедитесь, что оба сервера запущены.

## Часть 2. Целевая группа

Теперь объединим оба экземпляра в целевую группу. Позже балансировщик будет направлять запросы именно в неё.

### Шаг 4. Задайте тип и имя целевой группы

В разделе `Load Balancing` откройте `Target Groups` → `Create target group`:

1. `Choose a target type`: `Instances` (_10_). Мы направляем запросы на экземпляры EC2, поэтому другие типы целей не нужны.
2. `Target group name`: `web-tg` (_11_).
3. `Protocol` и `Port`: `HTTP` и `80` (_12_). На этот порт балансировщик будет отправлять запросы серверам.

![8.1.4. Тип и имя целевой группы](../_images/08/hands_on/ho1_04_tg_basic.jpg)

_8.1.4. Тип и имя целевой группы_

### Шаг 5. Настройте проверку работоспособности

Ниже укажите параметры проверки:

1. `VPC`: default VPC (_13_). Экземпляры и целевая группа должны находиться в одной VPC.
2. `Health check protocol`: `HTTP` (_14_).
3. `Health check path`: `/health` (_15_).

![8.1.5. Протокол и путь проверки](../_images/08/hands_on/ho1_05_tg_health.jpg)

_8.1.5. Протокол и путь проверки_

Откройте `Advanced health check settings`:

1. `Healthy threshold`: `2` (_16_) вместо `5` по умолчанию.
2. `Unhealthy threshold`: `2` (_17_).
3. `Timeout`: `5` секунд (_18_).
4. `Interval`: `10` секунд (_19_) вместо `30` по умолчанию.
5. `Success codes`: `200` (_20_).

![8.1.6. Пороги и интервал проверки](../_images/08/hands_on/ho1_06_tg_advanced.jpg)

_8.1.6. Пороги и интервал проверки_

Балансировщик проверяет каждый сервер раз в 10 секунд. Если сервер два раза подряд не ответит правильно, он будет отмечен как неисправный. После двух успешных проверок сервер сможет снова получать запросы.

Такой интервал удобен для демонстрации: изменения обычно видны за десятки секунд. В реальной системе частоту и пороги выбирают с учётом нагрузки и риска случайных сбоев.

### Шаг 6. Зарегистрируйте экземпляры

Нажмите `Next`. На странице `Register targets` выберите `web-1` и `web-2`. Проверьте порт `80` и нажмите `Include as pending below`.

Оба экземпляра появятся в `Review targets` (_21_), а счётчик покажет `2 pending` (_22_). Нажмите `Next` → `Create target group`.

![8.1.7. Регистрация экземпляров](../_images/08/hands_on/ho1_07_tg_register.jpg)

_8.1.7. Регистрация экземпляров_

Откройте `web-tg`. Сейчас у неё указано `Load balancer: None associated` (_23_), а экземпляры имеют состояние `Unused` (_24_).

![8.1.8. Цели без балансировщика](../_images/08/hands_on/ho1_08_tg_unused.jpg)

_8.1.8. Цели без балансировщика_

Это нормально. Целевая группа уже создана, но балансировщик к ней ещё не подключён. Пока некому проверять серверы и отправлять им запросы.

## Часть 3. Балансировщик

### Шаг 7. Выберите тип и схему

Перейдите в `Load Balancers` → `Create load balancer` и выберите `Application Load Balancer` → `Create`:

1. `Load balancer name`: `web-alb` (_25_). Это имя будет частью DNS-адреса.
2. `Scheme`: `Internet-facing` (_26_). Пользователи смогут обращаться к балансировщику из интернета. Вариант `Internal` предназначен для внутренних сервисов.
3. `Load balancer IP address type`: `IPv4` (_27_).

![8.1.9. Имя и схема балансировщика](../_images/08/hands_on/ho1_09_alb_basic.jpg)

_8.1.9. Имя и схема балансировщика_

### Шаг 8. Выберите зоны и подсети

В разделе `Network mapping` оставьте default VPC. Выберите две зоны и их подсети:

1. `eu-central-1a` (_28_).
2. `eu-central-1b` (_29_).

Для каждой подсети консоль показывает `Route table: IGW (✓)` (_30_). Это означает, что через Internet Gateway у подсети есть маршрут в интернет.

![8.1.10. Зоны и подсети балансировщика](../_images/08/hands_on/ho1_10_alb_network.jpg)

_8.1.10. Зоны и подсети балансировщика_

Балансировщик создаст узлы в обеих зонах. Если одна зона станет недоступна, узлы другой смогут продолжить работу. Для внешнего ALB нужны публичные подсети; сами веб-серверы при этом могут находиться в приватных.

Важно, чтобы зоны балансировщика включали зоны серверов. Например, сервер в `eu-central-1c` не будет получать запросы, если для балансировщика эта зона не включена.

### Шаг 9. Выберите Security Group и настройте listener

1. В `Security groups` уберите `default` и выберите `alb-sg` (_31_).
2. В `Listeners and routing` оставьте `HTTP`, порт `80` (_32_).
3. В `Default action` оставьте `Forward to target groups` (_33_). Другие возможные действия - `Redirect to URL` и `Return fixed response`.
4. В `Target group` выберите `web-tg` (_34_).

![8.1.11. Security Group и listener](../_images/08/hands_on/ho1_11_alb_sg_listener.jpg)

_8.1.11. Security Group и listener_

Теперь запросы на HTTP-порт балансировщика будут направляться в группу `web-tg`. Других правил маршрутизации мы не создаём.

Остальные параметры не меняйте. Нажмите `Create load balancer`.

### Шаг 10. Дождитесь готовности балансировщика

Откроется страница `web-alb`. Сначала статус будет `Provisioning` (_35_): AWS ещё создаёт балансировщик. Проверьте зоны в `Availability Zones` (_36_) и DNS-адрес в `DNS name` (_37_).

![8.1.12. Балансировщик создаётся](../_images/08/hands_on/ho1_12_alb_provisioning.jpg)

_8.1.12. Балансировщик создаётся_

Когда статус станет `Active`, перейдите на вкладку `Resource map`. Здесь показан путь запроса:

1. Listener `HTTP:80` (_38_).
2. Правило `Forward to target group` (_39_).
3. Целевая группа `web-tg` (_40_).
4. Экземпляры `web-1` и `web-2` со статусом `Healthy` (_41_).

![8.1.13. Карта ресурсов балансировщика](../_images/08/hands_on/ho1_13_resource_map.jpg)

_8.1.13. Карта ресурсов балансировщика_

Если цели показываются как `Unhealthy`, проверьте правило `web-sg` (источник `alb-sg`) и установку nginx через `User data`. Страница `/health` должна возвращать код 200.

## Часть 4. Проверка

Проверим работу из CloudShell. Для начала получите DNS-адрес балансировщика и сохраните его в переменной `ALB`:

```bash
ALB=$(aws elbv2 describe-load-balancers --names web-alb --query "LoadBalancers[0].DNSName" --output text); echo $ALB
```

> [!TIP]
> Если CloudShell перезапустится, значения переменных `ALB` и `TG` исчезнут. В этом случае выполните команды их создания ещё раз.

### Шаг 11. Проверьте распределение запросов

Отправьте шесть запросов к магазину и один запрос к странице проверки:

```bash
for i in 1 2 3 4 5 6; do curl -s http://$ALB/; echo; done
curl -i http://$ALB/health
```

![8.1.14. Ответы двух серверов через балансировщик](../_images/08/hands_on/ho1_14_curl_distribution.jpg)

_8.1.14. Ответы двух серверов через балансировщик_

В ответах должны встретиться зоны `eu-central-1a` и `eu-central-1b` (_42_). Значит, один адрес балансировщика ведёт к двум серверам. Ответы необязательно будут строго чередоваться: каждый новый запрос балансировщик может направить на любую исправную цель.

Для `/health` вы увидите `200 OK` (_43_) и текст `OK` (_44_). Такой ответ балансировщик ожидает от каждого сервера во время проверок.

### Шаг 12. Проверьте, что сервер недоступен напрямую

Получите публичный IP-адрес `web-1` и попробуйте обратиться к нему в обход балансировщика:

```bash
IP=$(aws ec2 describe-instances --filters Name=tag:Name,Values=web-1 Name=instance-state-name,Values=running --query "Reservations[].Instances[].PublicIpAddress" --output text); echo $IP
curl -m 5 http://$IP/
```

![8.1.15. Прямой запрос к серверу](../_images/08/hands_on/ho1_15_direct_timeout.jpg)

_8.1.15. Прямой запрос к серверу_

Первая команда показывает адрес сервера (_45_). Вторая завершится по таймауту через пять секунд (_46_): Security Group не разрешает входящий HTTP напрямую из интернета.

Через `web-alb` сервер доступен, а по собственному публичному адресу - нет. Значит, правила `alb-sg` и `web-sg` работают как задумано.

### Шаг 13. Остановите один сервер

Проверим отказ сервера. В консоли EC2 выберите `web-1` → `Instance state` → `Stop instance`. После остановки и обновления состояния целей повторите запросы из CloudShell. Выведем только зону сервера:

```bash
for i in $(seq 1 6); do curl -s -m 3 http://$ALB/ | grep -o 'Zone: [a-z0-9-]*'; done
```

![8.1.16. Все ответы из одной зоны](../_images/08/hands_on/ho1_16_after_stop.jpg)

_8.1.16. Все ответы из одной зоны_

Теперь отвечает только `eu-central-1b` (_47_). Сайт продолжает работать, хотя `web-1` остановлен.

Сразу после остановки некоторые запросы ещё могут завершаться ошибкой: балансировщику нужно время, чтобы обнаружить отказ. Именно для этого мы настраивали интервал и пороги проверки. После исключения сервера новые запросы идут к `web-2`.

Откройте `web-tg` → `Targets`. У `web-2` должен быть статус `Healthy` (_48_), у остановленного `web-1` - `Unused` (_49_), с пояснением `Target is in the stopped state`.

![8.1.17. Состояние целей после остановки web-1](../_images/08/hands_on/ho1_17_tg_one_stopped.jpg)

_8.1.17. Состояние целей после остановки web-1_

`Unused` здесь означает, что остановленный EC2 нельзя использовать как цель. `Unhealthy` означает другое: экземпляр работает, но не проходит HTTP-проверку. Во втором случае это можно увидеть на следующем шаге.

Запустите `web-1` снова через `Instance state` → `Start instance`. nginx запустится автоматически, так как мы включили его автозапуск. Когда сервер пройдёт две успешные проверки, балансировщик снова сможет отправлять ему запросы.

Проверьте состояния целей и распределение запросов в CloudShell:

```bash
TG=$(aws elbv2 describe-target-groups --names web-tg --query "TargetGroups[0].TargetGroupArn" --output text)
aws elbv2 describe-target-health --target-group-arn $TG --query "TargetHealthDescriptions[].[Target.Id,TargetHealth.State]" --output text
for i in $(seq 1 6); do curl -s -m 3 http://$ALB/ | grep -o 'Zone: [a-z0-9-]*'; done
```

![8.1.18. Сервер вернулся в работу](../_images/08/hands_on/ho1_18_recovered.jpg)

_8.1.18. Сервер вернулся в работу_

Обе цели снова `healthy` (_50_), а запросы приходят из обеих зон (_51_). Добавлять сервер в целевую группу заново не пришлось.

### Шаг 14. Сломайте проверку на всех серверах

Теперь проверим случай, когда обе цели не проходят проверку. Серверы оставим работающими, а путь проверки временно заменим на несуществующий `/missing`. nginx ответит на него кодом 404:

```bash
aws elbv2 modify-target-group --target-group-arn $TG --health-check-path /missing --query "TargetGroups[0].HealthCheckPath" --output text
```

То же самое можно сделать в `web-tg` → `Health checks` → `Edit`. После нескольких проверок посмотрите состояния целей и отправьте запросы:

```bash
aws elbv2 describe-target-health --target-group-arn $TG --query "TargetHealthDescriptions[].[Target.Id,TargetHealth.State,TargetHealth.Reason]" --output text
for i in $(seq 1 6); do curl -s -m 3 http://$ALB/ | grep -o 'Zone: [a-z0-9-]*'; done
```

![8.1.19. Fail open](../_images/08/hands_on/ho1_19_fail_open.jpg)

_8.1.19. Fail open_

Обе цели станут `unhealthy` с причиной `Target.ResponseCodeMismatch` (_52_). Но ответы главной страницы могут по-прежнему приходить с обоих серверов (_53_).

Это поведение называется _fail open_: когда все зарегистрированные цели не проходят проверки, ALB всё равно направляет им запросы. Оно позволяет избежать полной остановки только из-за ошибочной проверки, но не гарантирует, что само приложение работает.

Верните прежний путь проверки:

```bash
aws elbv2 modify-target-group --target-group-arn $TG --health-check-path /health --query "TargetGroups[0].HealthCheckPath" --output text
```

> [!IMPORTANT]
> `Fail open` не означает, что неисправности можно игнорировать. Если серверы действительно сломаны, пользователи будут получать ошибки. После проверки обязательно верните путь `/health`.

## Часть 5. Удаление ресурсов

Если сразу переходите к Hands-on 8.2, удалите только `web-1` и `web-2`. Балансировщик `web-alb`, группу `web-tg` и обе Security Group оставьте: они понадобятся дальше. Не откладывайте следующий hands-on надолго - балансировщик продолжает оплачиваться.

Если заканчиваете работу, удалите все ресурсы. Порядок важен: некоторые из них ссылаются друг на друга.

1. В `Load Balancers` удалите `web-alb`: `Actions` → `Delete load balancer`, затем введите `confirm`.
2. В `Instances` удалите `web-1` и `web-2`: `Instance state` → `Terminate (delete) instance`.
3. В `Target Groups` удалите `web-tg` через `Actions` → `Delete`.
4. В `Security Groups` удалите сначала `web-sg`, затем `alb-sg`.

Если AWS сообщает, что ресурс ещё используется, подождите завершения удаления экземпляров и сетевых интерфейсов и повторите попытку.

Убедитесь, что `web-alb` и `web-tg` удалены, а оба экземпляра имеют состояние `Terminated`.
