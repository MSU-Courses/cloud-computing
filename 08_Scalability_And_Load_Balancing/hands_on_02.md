# Hands-on 8.2. Группа Auto Scaling

В Hands-on 8.1 мы настроили балансировщик для двух серверов. При отказе одного из них сайт продолжал работать, но запускать сервер взамен пришлось вручную.

Теперь эту задачу будет выполнять Amazon EC2 Auto Scaling: группа сама поддерживает нужное число экземпляров и изменяет его при росте нагрузки.

Мы подключим группу к `web-alb`, создадим нагрузку на процессоры и посмотрим, как число экземпляров увеличится, а затем уменьшится. В конце удалим один экземпляр и проверим, запустит ли группа замену.

## Что получится в конце

- Роль IAM `web-ssm-role` для выполнения команд на экземплярах через AWS Systems Manager без SSH.
- Шаблон запуска `web-lt` с nginx и параметрами будущих экземпляров.
- Группа Auto Scaling `web-asg` в двух зонах доступности: минимум 2, максимум 4 экземпляра.
- Политика `cpu-50`, которая стремится поддерживать среднюю загрузку CPU около 50%.
- Подключение группы к `web-tg`, чтобы новые экземпляры автоматически получали запросы через `web-alb`.

## Перед началом

- Выполнен Hands-on 8.1. Остались `web-alb`, `web-tg`, `alb-sg` и `web-sg`; экземпляры `web-1` и `web-2` удалены.
- В `web-tg` настроена проверка `/health`. Если вы меняли путь на `/missing`, верните его обратно.
- Вы знакомы с IAM Role и instance profile из главы 4.
- Выбран регион `Europe (Frankfurt)`.
- Для занятия предусмотрено около полутора часов, но автоматическое сокращение группы может потребовать дополнительного ожидания.

> [!WARNING]
> Экземпляры, балансировщик, публичные IPv4-адреса и некоторые возможности CloudWatch платные. Во время опыта группа может вырасти до четырёх `t3.micro`. У этого типа есть CPU-кредиты: длительная высокая нагрузка в режиме `unlimited` может вызвать дополнительные расходы. После занятия обязательно выполните часть 6.

## Часть 1. Подготовка

### Шаг 1. Создайте роль для экземпляров

Чтобы запустить команду сразу на нескольких серверах, используем AWS Systems Manager. Он позволяет управлять экземплярами без SSH и открытых входящих портов. Агент Systems Manager уже установлен в Amazon Linux 2023, но для подключения ему нужны разрешения - роль IAM с соответствующей политикой.

Создадим IAM Role и передадим её экземплярам через instance profile.

Перейдите в `IAM` → `Roles` → `Create role`:

1. `Trusted entity type`: `AWS service` (_1_).
2. `Service or use case`: `EC2` (_2_).
3. `Use case`: `EC2` (_3_).

![8.2.1. Доверенная сущность роли](../_images/08/hands_on/ho2_01_role_trust.jpg)

_8.2.1. Доверенная сущность роли_

Мы выбираем обычную роль для EC2 и сами добавляем разрешения. Вариант `EC2 Role for AWS Systems Manager` также подходит, но часть настроек делает автоматически.

Нажмите `Next`, найдите политику `AmazonSSMManagedInstanceCore` и отметьте её (_4_). Это управляемая политика AWS (_5_), которая разрешает агенту подключаться к Systems Manager и получать команды.

В политике доверия вы увидите `sts:AssumeRole` (_7_) и `ec2.amazonaws.com` (_8_). Это означает, что роль разрешено принимать сервису EC2 от имени экземпляров. Нажмите `Create role`. Консоль также создаст instance profile с именем `web-ssm-role`.

### Шаг 2. Уменьшите задержку отмены регистрации

Когда балансировщик выводит сервер из целевой группы, он некоторое время ждёт завершения уже начатых запросов. Это называется _deregistration delay_. По умолчанию время ожидания - 300 секунд.

Для нашего простого сайта уменьшим задержку до 30 секунд, чтобы сокращение группы происходило быстрее.

Откройте `web-tg` → `Attributes` → `Edit`. В поле `Deregistration delay (draining interval)` введите `30` (_9_) и сохраните.

![8.2.4. Задержка отмены регистрации](../_images/08/hands_on/ho2_04_dereg_delay.jpg)

_8.2.4. Задержка отмены регистрации_

Наша страница открывается быстро, поэтому 30 секунд достаточно. В настоящем приложении нужно учитывать длительные запросы: слишком короткая задержка может прервать их.

Здесь же видно, что выбран алгоритм `Round robin` (_10_) - балансировщик распределяет запросы между целями по очереди.

### Шаг 6. Задайте роль, мониторинг и user data

Откройте `Advanced details`:

1. В `IAM instance profile` выберите `web-ssm-role` (_18_).

![8.2.8. Роль экземпляров в шаблоне](../_images/08/hands_on/ho2_08_lt_iam.jpg)

_8.2.8. Роль экземпляров в шаблоне_

2. В `Detailed CloudWatch monitoring` выберите `Enable` (_19_). Эта настройка оплачивается отдельно.
3. В `Credit specification` оставьте `Don't include in launch template` (_20_). Для `t3.micro` будет применён режим CPU-кредитов `unlimited` по умолчанию.

![8.2.9. Детальный мониторинг](../_images/08/hands_on/ho2_09_lt_monitoring.jpg)

_8.2.9. Детальный мониторинг_

Детальный мониторинг отправляет данные о загрузке CPU каждую минуту вместо пяти минут. Благодаря этому политика Auto Scaling сможет быстрее заметить изменение нагрузки.

4. В поле `User data` вставьте скрипт (_21_):

```bash
#!/bin/bash
dnf install -y nginx
dnf install -y stress-ng
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
AZ=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone)
echo "<h1>$(hostname)</h1><p>Zone: $AZ</p>" > /usr/share/nginx/html/index.html
echo "OK" > /usr/share/nginx/html/health
systemctl enable --now nginx
```

![8.2.10. User data шаблона](../_images/08/hands_on/ho2_10_lt_userdata.jpg)

_8.2.10. User data шаблона_

Скрипт устанавливает nginx, создаёт главную страницу и `/health`. Новая строка (_22_) устанавливает `stress-ng` - утилиту, которой мы создадим высокую загрузку CPU на существующих экземплярах.

Нажмите `Create launch template`.

## Часть 3. Группа Auto Scaling

### Шаг 7. Выберите шаблон

Перейдите в `Auto Scaling Groups` → `Create Auto Scaling group`:

1. `Auto Scaling group name`: `web-asg` (_23_).
2. `Launch template`: `web-lt` (_24_).
3. `Version`: `Default (1)` (_25_).

![8.2.11. Шаблон для группы](../_images/08/hands_on/ho2_11_asg_template.jpg)

_8.2.11. Шаблон для группы_

`Default (1)` означает, что новые экземпляры будут запускаться по первой версии шаблона. Позже можно создать новую версию и сделать её версией по умолчанию. Уже запущенные экземпляры от этого сами не изменятся.

Вариант `Latest` всегда использует самую новую версию, даже если её ещё не проверили. Поэтому для занятия выбираем `Default`.

Нажмите `Next`.

### Шаг 8. Выберите подсети

В `VPC` оставьте default VPC (_26_). В `Availability Zones and subnets` выберите подсети `eu-central-1a` и `eu-central-1b` (_27_).

![8.2.12. Подсети группы](../_images/08/hands_on/ho2_12_asg_network.jpg)

_8.2.12. Подсети группы_

Группа постарается распределить экземпляры между этими зонами равномерно. Например, при желаемом размере 2 она разместит по одному экземпляру в каждой зоне.

Нажмите `Next`.

### Шаг 9. Подключите группу к балансировщику

1. В `Load balancing` выберите `Attach to an existing load balancer` (_28_).
2. В `Existing load balancer target groups` укажите `web-tg` (_29_).

![8.2.13. Подключение к целевой группе](../_images/08/hands_on/ho2_13_asg_lb.jpg)

_8.2.13. Подключение к целевой группе_

Группу Auto Scaling подключают к _целевой группе_, а не напрямую к адресу ALB. После подключения новые экземпляры автоматически регистрируются в `web-tg`; вручную добавлять их не нужно.

В разделе `Health checks`:

1. Проверки EC2 уже включены (_30_).
2. Включите `Turn on Elastic Load Balancing health checks` (_31_).
3. `Health check grace period`: `300` секунд (_32_).

![8.2.14. Проверки работоспособности группы](../_images/08/hands_on/ho2_14_asg_health.jpg)

_8.2.14. Проверки работоспособности группы_

Разница между проверками важна:

- _EC2 health checks_ определяют, исправен ли сам экземпляр.
- _ELB health checks_ проверяют, может ли веб-сервер отвечать на HTTP-запросы.

Если nginx перестанет работать, ELB обнаружит проблему, а Auto Scaling сможет заменить экземпляр. Период `300` секунд даёт новому серверу время на запуск и установку nginx. Он не отменяет замену явно остановленного или удалённого EC2.

Нажмите `Next`.

### Шаг 10. Задайте размер и политику масштабирования

1. `Desired capacity`: `2` (_33_).
2. `Min desired capacity`: `2` (_34_).
3. `Max desired capacity`: `4` (_35_).

![8.2.15. Размер группы](../_images/08/hands_on/ho2_15_asg_size.jpg)

_8.2.15. Размер группы_

Эти значения означают:

- _Desired = 2_. Сейчас группа должна поддерживать два экземпляра.
- _Min = 2_. Даже при низкой нагрузке останутся как минимум два экземпляра.
- _Max = 4_. При росте нагрузки группа сможет увеличить их число, но не больше четырёх.

Так мы обеспечим по одному серверу в двух зонах и ограничим расходы.

В разделе `Automatic scaling` настройте политику:

1. Выберите `Target tracking scaling policy` (_36_), имя `cpu-50`.
2. `Metric type`: `Average CPU utilization` (_37_).
3. `Target value`: `50` (_38_).
4. `Instance warmup`: `60` секунд (_39_).

![8.2.16. Политика target tracking](../_images/08/hands_on/ho2_16_asg_policy.jpg)

_8.2.16. Политика target tracking_

Политика `cpu-50` старается удерживать среднюю загрузку CPU около 50%. Если нагрузка долго выше цели, группа добавляет экземпляры. Если ниже - постепенно убирает лишние, но не меньше двух.

`Instance warmup = 60` секунд - время, которое даём новому серверу после запуска, прежде чем полноценно учитывать его в расчётах политики. Для нашего nginx этого обычно достаточно. Не путайте с `Health check grace period`: тот защищает новый экземпляр от слишком ранней замены по неудачным проверкам.

В `Additional settings` включите `Enable group metrics collection within CloudWatch` (_40_). Тогда в мониторинге будут видны не только показатели отдельных серверов, но и число экземпляров группы.

![8.2.17. Метрики группы](../_images/08/hands_on/ho2_17_asg_metrics.jpg)

_8.2.17. Метрики группы_

Нажмите `Skip to review`, проверьте настройки и выберите `Create Auto Scaling group`.

### Шаг 11. Убедитесь, что политика создана

Иногда при создании первой группы Auto Scaling консоль сообщает: группа создана, но политика масштабирования не создана (_41_). Это может произойти, пока AWS подготавливает служебную роль `AWSServiceRoleForAutoScaling`. В это время группа может показывать `Updating capacity` (_42_), желаемый размер `2` (_43_) и пока не иметь экземпляров.

Если такого сообщения нет, переходите к шагу 12.

## Часть 4. Нагрузочный тест

### Шаг 13. Проверьте балансировщик и агент Systems Manager

Откройте CloudShell. Получите DNS-адрес `web-alb`, отправьте шесть запросов и проверьте, видит ли Systems Manager новые экземпляры. `sed` уберёт HTML-теги из ответов:

```bash
ALB=$(aws elbv2 describe-load-balancers --names web-alb --query "LoadBalancers[0].DNSName" --output text)
for i in $(seq 1 6); do curl -s -m 3 http://$ALB/ | sed 's/<[^>]*>/ /g'; done
aws ssm describe-instance-information --query "InstanceInformationList[].[InstanceId,PingStatus]" --output text
```

![8.2.22. Ответы экземпляров группы и агенты Systems Manager](../_images/08/hands_on/ho2_22_alb_and_ssm.jpg)

_8.2.22. Ответы экземпляров группы и агенты Systems Manager_

В ответах видны два сервера из разных зон (_55_). Их автоматически зарегистрировала группа Auto Scaling.

Команда Systems Manager показывает состояние `Online` (_56_) для обоих экземпляров. Если список пока пуст, проверьте ещё раз после запуска агента. Также убедитесь, что экземплярам назначена роль `web-ssm-role` и у них есть сетевой доступ к сервису.

### Шаг 14. Нагрузите процессоры

Теперь создадим высокую загрузку CPU на работающих экземплярах `web-asg`:

```bash
aws ssm send-command \
  --document-name AWS-RunShellScript \
  --targets Key=tag:aws:autoscaling:groupName,Values=web-asg \
  --parameters 'commands=["stress-ng --cpu 0 --timeout 15m"]' \
  --query "Command.[CommandId,Status]" --output text
```

В команде используются три важных параметра:

- `AWS-RunShellScript` - документ Systems Manager для выполнения команд Linux.
- `--targets` - выбор всех текущих экземпляров группы по тегу `aws:autoscaling:groupName`.
- `stress-ng --cpu 0 --timeout 15m` - нагрузка на все доступные vCPU на 15 минут.

После отправки команда вернёт идентификатор и состояние `Pending` (_57_). Подставьте полученный идентификатор в переменную `CMD` и посмотрите состояние выполнения:

```bash
CMD="вставьте_идентификатор_команды"
aws ssm list-command-invocations --command-id $CMD --query "CommandInvocations[].[InstanceId,Status]" --output text
```

Статус `InProgress` (_58_) означает, что `stress-ng` выполняется. Нагрузка автоматически прекратится через 15 минут.

### Шаг 15. Посмотрите на метрику и тревогу

Спустя несколько минут проверьте среднюю загрузку CPU и состояние тревог CloudWatch:

```bash
aws cloudwatch get-metric-statistics --namespace AWS/EC2 --metric-name CPUUtilization \
  --dimensions Name=AutoScalingGroupName,Value=web-asg \
  --start-time $(date -u -d '-10 min' +%FT%TZ) --end-time $(date -u +%FT%TZ) \
  --period 60 --statistics Average \
  --query "sort_by(Datapoints,&Timestamp)[].[Timestamp,Average]" --output text
aws cloudwatch describe-alarms --alarm-name-prefix TargetTracking-web-asg --query "MetricAlarms[].[AlarmName,StateValue]" --output text
```

![8.2.24. Загрузка процессора и тревога](../_images/08/hands_on/ho2_24_cpu_alarm.jpg)

_8.2.24. Загрузка процессора и тревога_

В нашем примере CPU загружен почти на 100% (_59_), а тревога с `AlarmHigh` в имени перешла в `ALARM` (_60_). Значит, нагрузка превысила уровень, на который рассчитана политика масштабирования.

Тревоги для политики `cpu-50` создал AWS автоматически. Посмотрите их настройки:

```bash
aws cloudwatch describe-alarms --alarm-name-prefix TargetTracking-web-asg \
  --query "MetricAlarms[].[StateValue,ComparisonOperator,Threshold,Period,EvaluationPeriods,DatapointsToAlarm]" --output text
```

![8.2.25. Пороги тревог политики](../_images/08/hands_on/ho2_25_alarm_thresholds.jpg)

_8.2.25. Пороги тревог политики_

На скриншоте видно два разных условия:

- _Рост_ (_61_). Тревога реагирует на три последовательных минутных значения выше 50%.
- _Сокращение_ (_62_). Тревога ждёт 15 последовательных значений ниже 37,5%.

Поэтому группа быстрее добавляет серверы и осторожнее удаляет их. Эти пороги показаны для созданной в занятии политики: AWS управляет тревогами автоматически, их не нужно настраивать вручную. `None` в последнем столбце означает, что отдельное число точек для срабатывания не задано.

### Шаг 16. Посмотрите, как выросла группа

Откройте `web-asg` → `Activity`. Вы увидите запуск ещё двух экземпляров (_63_). В `Cause` указано (_64_), что политика `cpu-50` увеличила желаемый размер с 2 до 4 после тревоги `AlarmHigh`.

Пока новые экземпляры запускаются, их состояние может быть `Waiting for instance warmup`.

![8.2.26. Группа выросла до четырёх экземпляров](../_images/08/hands_on/ho2_26_scale_out.jpg)

_8.2.26. Группа выросла до четырёх экземпляров_

Почему группа добавила сразу два экземпляра? На двух серверах загрузка была около 100%. Чтобы приблизиться к цели 50% при такой же общей работе, в идеальном случае понадобятся четыре сервера: `2 × 100 / 50 = 4`. Это также наш максимальный размер группы.

Перейдите в `web-tg` → `Targets`. Там должны появиться четыре исправные цели (_65_), по две в каждой зоне (_66_). Если в столбце `Name` стоит прочерк, это нормально: мы не задавали экземплярам тег `Name`.

![8.2.27. Четыре цели в целевой группе](../_images/08/hands_on/ho2_27_tg_four.jpg)

_8.2.27. Четыре цели в целевой группе_

Здесь есть особенность опыта. Команда `stress-ng` была отправлена только на два первоначальных экземпляра. Новые серверы не выполняют её и почти не нагружены. Поэтому среднее значение стало примерно `(100 + 100 + 0 + 0) / 4 = 50%`.

В настоящем веб-приложении нагрузку обычно создают запросы пользователей. Балансировщик отправлял бы часть новых запросов и новым серверам.

## Часть 5. Замена и сокращение

### Шаг 17. Удалите экземпляр вручную

Проверим, что Auto Scaling заменяет потерянные экземпляры. Пока работает `stress-ng`, выберите _один из двух серверов, созданных при увеличении группы_. На них нет искусственной нагрузки, поэтому удаление меньше повлияет на среднюю загрузку CPU.

Если удалить один из первоначальных нагруженных серверов, средняя загрузка снизится сильнее и группа может начать сокращаться раньше.

Откройте `Instances`, найдите экземпляр по идентификатору (_67_) и выберите `Instance state` → `Terminate (delete) instance` (_68_). Подтвердите действие.

![8.2.28. Удаление экземпляра группы](../_images/08/hands_on/ho2_28_terminate.jpg)

_8.2.28. Удаление экземпляра группы_

Вернитесь на вкладку `Activity` группы. В истории должны появиться две записи: экземпляр признан потерянным (_69_), а вместо него запускается новый (_70_). Желаемый размер остаётся `4`: группа восстанавливает недостающее количество сама.

![8.2.29. Замена удалённого экземпляра](../_images/08/hands_on/ho2_29_replacement.jpg)

_8.2.29. Замена удалённого экземпляра_

Группа заменяет экземпляр независимо от причины его исчезновения - сбой это или ручное удаление. _Чтобы уменьшить число серверов, нужно менять желаемый размер группы, а не удалять EC2 вручную._

### Шаг 18. Дождитесь сокращения группы

Через 15 минут после запуска `stress-ng` завершит работу. Загрузка CPU упадёт. Если она остаётся низкой, тревога на сокращение со временем перейдёт в `ALARM`.

Проверить её можно командой `describe-alarms` из шага 15. Сокращение не начинается немедленно: политика специально ждёт устойчивого снижения нагрузки.

Откройте `web-asg` → `Activity`. В нашем примере политика сначала снизила желаемый размер с 4 до 3 (_71_), затем с 3 до 2 (_72_). Пока экземпляр удаляется, может отображаться `In progress`: балансировщик завершает его регистрацию и ждёт установленную задержку 30 секунд.

![8.2.30. Сокращение группы](../_images/08/hands_on/ho2_30_scale_in.jpg)

_8.2.30. Сокращение группы_

При сокращении группа старается сохранить равномерное распределение по зонам. В результате в `eu-central-1a` и `eu-central-1b` останется по одному экземпляру.

Скорость и число шагов сокращения могут отличаться от скриншота: они зависят от метрик и работы политики. Главное - группа сама вернулась к размеру, подходящему для низкой нагрузки.

Ниже двух экземпляров группа не опустится, потому что `Min desired capacity = 2`.

## Часть 6. Удаление ресурсов

В завершение удалите ресурсы, чтобы прекратить начисление платы. Начните с группы Auto Scaling: пока она существует, она будет автоматически заменять удалённые вручную экземпляры.

1. В `Auto Scaling Groups` удалите `web-asg` через `Actions` → `Delete` и введите `delete`. Убедитесь, что созданные группой экземпляры перешли в состояние `Terminated`.
2. В `Launch Templates` удалите `web-lt` через `Actions` → `Delete template`.
3. Удалите `web-alb`, `web-tg`, `web-sg` и `alb-sg` в том же порядке, что в части 5 Hands-on 8.1.
4. В `IAM` → `Roles` удалите `web-ssm-role`.

Роль `AWSServiceRoleForAutoScaling` оставьте: это служебная роль AWS, она не оплачивается и может пригодиться позже.

Проверьте, что `web-asg`, `web-lt`, `web-alb` и `web-tg` удалены, а все созданные экземпляры находятся в состоянии `Terminated`.
