# Лабораторная работа №6. Масштабирование и балансировка нагрузки. Elastic Load Balancing, Amazon EC2 Auto Scaling

## Цель работы

Научиться распределять запросы между серверами с помощью Application Load Balancer и поручать Amazon EC2 Auto Scaling добавлять и убирать серверы по нагрузке. Запустить приложение на нескольких серверах так, чтобы пользователь не терял вход, на какой бы сервер ни попал его запрос.

## Как устроена работа

| Уровень     | Что нужно сделать              | Максимальная оценка |
| ----------- | ------------------------------ | ------------------- |
| Базовый     | Часть 1: задания 1-3           | 7                   |
| Продвинутый | Часть 1 и Часть 2: задания 1-7 | 10                  |

Часть 1 учебная. Вы запускаете простые серверы с nginx за балансировщиком, нагружаете их и смотрите, как группа растёт и уменьшается, а в конце удаляете всё, что создали. В Части 2 то же самое происходит с вашим приложением.

> [!IMPORTANT]
> Серверы должны принимать HTTP только от балансировщика, а SSH - только с `bastion`. Команды выполняйте на своём компьютере (в Windows - в Git Bash) или на `bastion`. CloudShell не используйте.

## Что вы построите

- _Application Load Balancer_ работает в двух публичных подсетях. Пользователи обращаются к нему по DNS-имени, а он передаёт запросы исправным серверам.
- _Группа Auto Scaling_ держит от двух до четырёх серверов в двух зонах. Она добавляет серверы, когда запросов становится больше, и убирает их, когда запросов становится меньше.
- _Таблица DynamoDB_ (Часть 2) хранит сессии пользователей. Благодаря ей любой сервер может обработать любой запрос.

## Сколько это стоит

В таблице приведены цены для региона `eu-central-1` на октябрь 2026 года.

| Ресурс                                | Как оплачивается                            |
| ------------------------------------- | ------------------------------------------- |
| Application Load Balancer             | ≈ $0,027 в час, пока существует             |
| Публичные адреса узлов балансировщика | ≈ $0,005 в час за каждый, по одному на зону |
| Сервер `t3.micro` с публичным адресом | ≈ $0,017 в час, пока работает               |

Одно занятие с балансировщиком и двумя-четырьмя серверами стоит меньше $0,5.

> Балансировщик нельзя остановить: пока он существует, он стоит около $0,9 в сутки. Поэтому удаляйте балансировщик и группу в конце каждого занятия.

## Часть 1. Базовый уровень

### Задание 1. Балансировщик

Балансировщик - это единая точка входа. Он принимает запросы пользователей и передаёт их серверам из целевой группы. Серверов пока нет, их запустит группа Auto Scaling в задании 2.

1. _Создайте целевую группу_ `lab6-tg` в VPC из ЛР3. Тип целей - `Instances`, а запросы серверам она передаёт по HTTP на порт 80. Настройте проверку работоспособности так, чтобы она обращалась к пути `/health` каждые 10 секунд.
2. _Создайте балансировщик_ `lab6-alb` типа `Application Load Balancer` со схемой `Internet-facing` в подсетях `public-a` и `public-b`. Добавьте listener, который принимает HTTP на порту 80 и передаёт запросы в `lab6-tg`. Балансировщик должен принимать HTTP из любого места.
3. _Откройте_ в браузере адрес из поля `DNS name` балансировщика.

> Какой ответ вернул балансировщик и почему? Зачем ему подсети в двух зонах?

### Задание 2. Группа Auto Scaling

Группа запускает виртуальные машины сама, без вас. Поэтому всё, что вы раньше выбирали при запуске экземпляра, нужно заранее сохранить в шаблоне запуска.

1. _Создайте шаблон запуска_ `lab6-lt` для сервера Amazon Linux 2023 типа `t3.micro` с вашей парой ключей. Подсеть в шаблоне не указывайте: её выберет группа. HTTP сервер должен принимать только от балансировщика. В поле `User data` вставьте скрипт, который устанавливает nginx и выводит на странице имя сервера и его зону:

   ```bash
   #!/bin/bash
   dnf install -y nginx
   TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
   AZ=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone)
   echo "<h1>$(hostname)</h1><p>Zone: $AZ</p>" > /usr/share/nginx/html/index.html
   echo "OK" > /usr/share/nginx/html/health
   systemctl enable --now nginx
   ```

2. _Создайте группу_ `lab6-asg` из этого шаблона, которая запускает серверы в подсетях `public-a` и `public-b` и регистрирует их в целевой группе `lab6-tg`. Включите проверки ELB (`Elastic Load Balancing health checks`), чтобы группа заменяла серверы, которые не прошли проверку балансировщика. Задайте размер группы:
   1. Желаемое количество серверов `2`,
   2. Минимальное количество серверов `2`,
   3. Максимальное количество серверов `4`.
3. _Добавьте группе политику target tracking_, которая следит за метрикой `Application Load Balancer request count per target` и держит её около значения 50.
4. _Дождитесь_, пока обе цели в `lab6-tg` перейдут в состояние `healthy`.
5. _Обновите страницу балансировщика_ несколько раз и посмотрите, какие серверы вам отвечают.

Политика target tracking держит выбранную метрику около целевого значения, в нашем случае около 50 запросов в минуту на один сервер. Для этого она сама создаёт в CloudWatch две тревоги: `AlarmHigh` срабатывает, когда запросов слишком много, и добавляет серверы, а `AlarmLow` срабатывает, когда запросов мало, и убирает лишние.

> Чем группа Auto Scaling отличается от целевой группы? Почему в шаблоне нет подсети?

### Задание 3. Нагрузка

Теперь дайте серверам нагрузку и посмотрите, как группа на неё реагирует.

1. _Запустите нагрузку_ с `bastion` или со своего компьютера. Скрипт ниже десять минут подряд отправляет запросы балансировщику:

   ```bash
   ALB=<DNS-имя балансировщика>
   end=$((SECONDS+600)); while [ $SECONDS -lt $end ]; do curl -s -o /dev/null http://$ALB/; done
   ```

   Можно и просто быстро обновлять страницу в браузере, но скрипт даёт ровную нагрузку.

2. _Посмотрите тревоги_ в разделе `CloudWatch` → `Alarms`. На вкладке `History` видно, какая тревога перешла в состояние `ALARM` и когда это произошло, а на странице тревоги - график метрики `RequestCountPerTarget`.
3. _Посмотрите историю группы_ на вкладке `Activity`. В поле `Cause` указано, почему группа запустила новые серверы.
4. _Дождитесь_, пока после окончания нагрузки группа вернётся к двум серверам. Обычно это занимает 15-20 минут.

> Сколько серверов запустила группа и почему не больше четырёх? Почему метрика упала после запуска новых серверов, хотя запросов не стало меньше? Почему группа добавляет серверы быстрее, чем убирает?

## Часть 2. Продвинутый уровень

Вложения приложения уже хранятся в S3, а данные в RDS. На `app-server` осталось одно: сессии пользователей лежат файлами на его диске. Если серверов станет несколько, пользователь, который вошёл на одном сервере, на другом будет не залогинен. Поэтому,

### Задание 4. Сессии в DynamoDB

Amazon DynamoDB - это управляемая NoSQL-база данных вида "ключ - значение". Серверов у неё нет: вы создаёте только таблицу и платите за запросы к ней. Каждая сессия хранится в таблице отдельным элементом, а ключом элемента служит идентификатор сессии. Чтобы старые сессии не копились, в таблице включают TTL: DynamoDB сам удаляет элементы, срок которых истёк.

Имена ключа и атрибута TTL зависят от библиотеки, которую использует ваш вариант приложения.

| Вариант приложения                                                              | Ключ таблицы | Атрибут TTL  |
| ------------------------------------------------------------------------------- | ------------ | ------------ |
| `open_capsules_php_functional`, `open_capsules_php_oop`, `open_capsules_nodejs` | `id`         | `expires`    |
| `open_capsules_php_laravel`                                                     | `key`        | `expires_at` |

1. _Создайте таблицу_ `timecapsule-dev-sessions` с ключом типа `String` в режиме `On-demand` и включите для неё TTL.
2. _Создайте политику_ `timecapsule-dev-app-sessions`, которая разрешает для этой таблицы только `GetItem`, `PutItem`, `UpdateItem` и `DeleteItem`, и прикрепите её к роли `timecapsule-dev-app-role`.
3. _Перенесите сессии в таблицу_. Добавьте в `.env` имя таблицы и замените в коде хранилище сессий так, как описано для вашего варианта:

   | Вариант приложения             | Что сделать                                                                                                                                                                                            |
   | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
   | `open_capsules_php_functional` | В `src/bootstrap.php` вместо вызова `session_save_path()` зарегистрируйте обработчик `Aws\DynamoDb\SessionHandler::fromClient(...)` с параметром `table_name`. Это нужно сделать до `session_start()`. |
   | `open_capsules_php_oop`        | Сделайте то же самое в файле `src/Session.php`.                                                                                                                                                        |
   | `open_capsules_php_laravel`    | Укажите в `.env` `SESSION_DRIVER=dynamodb` и добавьте хранилище `dynamodb` в `config/cache.php` по документации Laravel, не указывая в нём ключи доступа.                                              |
   | `open_capsules_nodejs`         | В `src/app.js` замените `session-file-store` пакетом `connect-dynamodb` и передайте ему параметры `table` и `initialized: true`.                                                                       |

   Ключи доступа не нужны: SDK возьмёт учётные данные роли, как в ЛР4.

4. _Выпустите новую версию_ на `app-server` своим способом из ЛР2-ЛР5.
5. _Войдите в приложение_ и найдите свою сессию в таблице с помощью `Explore table items`.

> Почему сессии нельзя оставить в файлах, когда серверов несколько? Зачем Node.js нужен `initialized: true`?

2. _Создайте шаблон_ `timecapsule-dev-app-lt` из этого образа для сервера типа `t3.micro` с ролью `timecapsule-dev-app-role`. Доступ у серверов должен быть таким же, как у `app-server`, в том числе к базе, но HTTP они должны принимать только от балансировщика.

## Частые проблемы и их решения

| Симптом                             | Что проверить                                                                                                                                |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Балансировщик отвечает `503`        | В целевой группе нет исправных целей. Возможно, группа ещё не запустила серверы или не подключена к целевой группе.                          |
| Цель `unhealthy`                    | Сервер не принимает HTTP от балансировщика или nginx на нём не запущен. Для приложения причиной может быть и то, что не работает база.       |
| Группа создана, а политики нет      | AWS ещё готовил служебную роль для Auto Scaling. Подождите несколько минут и добавьте политику на вкладке `Automatic scaling`.               |
| Группа не растёт под нагрузкой      | Нагрузка слишком слабая. Запустите скрипт сразу в двух окнах.                                                                                |
| `AccessDeniedException` от DynamoDB | Политика не прикреплена к роли или в ней указана другая таблица. В Node.js причиной может быть ещё и то, что не передан `initialized: true`. |
| Вход теряется при смене сервера     | Образ был создан до того, как вы выпустили версию с сессиями в DynamoDB.                                                                     |
